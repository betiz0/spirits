OpenSpec の変更について、実装が change の成果物（specs, tasks, design）の意図を満たしているかを深く検証する。

既定の `/opsx-verify`（以下 verify1）は、キーワード検索と推論による軽量な確認で、迷ったら重大度を下げる方針をとる。このスキルはその後段で、コードを読み、テストを実行し、spec 外の変更まで調べる。archive に進めるかどうかは、このスキルの判定で決める。

## 基本姿勢

- 読み取り専用。コード・テスト・成果物を変更しない。修正は apply 工程で行う。
- 判断はコードの挙動とテストの実行結果に基づく。キーワードの一致やファイル名を、実装の証拠として扱わない。
- 迷ったときに重大度を下げない。根拠が足りない指摘は重大度を保ったまま `[要確認]` を付け、何を確かめれば決着するかを書く。
- spec が正しいとは仮定しない。実装を読む中で見えた spec 自体の矛盾・欠落・曖昧さは、`SPEC` 区分で実装の不具合と分けて報告する。
- 構造は、抽象化の追加と重複の蓄積の両方向から見る。デザインパターン名の有無や一般則では判断せず、増えた間接層と、それで得たものとを比べる。
- コードスタイルの細部は扱わない（verify1 の担当）。

## 入力

- **変更名**：省略時は会話から推定する。候補が複数あれば `openspec list --json` で一覧を出し、利用者に選ばせる。
- **verify1 のレポートのパス**（任意）：Phase C まで開かない。
- **前回の verify2 レポートのパス**（任意）：渡された場合は「再検証モード」で動く。

引数は `/skill:sprt-opsx-verify-deep <change-name>` で渡され、Pi では `User: <args>` として本文末尾に付く。

ストア（登録済みの独立 OpenSpec リポジトリ）を使っている場合は、既定の verify と同じく、specs と changes を扱う openspec コマンドに `--store <id>` を付ける。

## Phase A：準備

1. 変更を選び、`Using change: <name>` と告げる。
2. `openspec status --change "<name>" --json` で、スキーマと成果物の有無を確認する。
3. `openspec instructions apply --change "<name>" --json` を実行し、`contextFiles` に列挙された成果物をすべて読む。
4. 検証対象の差分を確定する。
   - 既定ブランチ（main など）を特定し、`git merge-base HEAD <既定ブランチ>` で基点コミットを得る。特定できなければ利用者に確認する。
   - `git rev-parse HEAD` で現在の HEAD を記録する。
   - `git diff <基点コミット>` で、コミット済みと未コミットの変更をまとめて取得する。
   - `git status --porcelain` で未追跡の新規ファイルを洗い出し、内容を読む（`git diff` には出ないため）。
   - `openspec/` 配下の成果物の変更は、B-4 の対象から外す。
   - 基点コミットとHEADが同じで、未コミットの変更も無い場合（main へ直接コミットした後など）は、change の作成以降のコミット範囲を利用者に確認する。
5. テストコマンドを特定する。`openspec/config.yaml`、`AGENTS.override.md`、`AGENTS.md`、`CLAUDE.md`、ビルド定義（package.json、pyproject.toml、Makefile など）の順に探す。特定できなければ利用者に確認する。
6. 規約正本を探す。次の順に確認し、最初に見つかったものを正本とする。
   - `openspec/config.yaml`、`AGENTS.override.md`、`AGENTS.md` が参照している規約ファイル
   - `docs/architecture/convention-registry.md`（architecture-guards の既定の置き場所）

   見つかった場合の手順は次のとおり。見つからなければ「規約正本なし」と記録し、規約に関する確認（B-1 の規約検査、B-3 の規約の弱体化、B-7 の規約違反の判定）を省略する。
   - 正本を全文読み、各規約の ID・強度（`must` / `should` / `info`）・判定方法を把握する。
   - 基点コミット時点の正本を `git show <基点コミット>:<正本のパス>` で読み、差分の有無を記録する。
7. design.md の Decisions から、計画された継ぎ目（B-7 の定義に当たるもの）を一覧にする。

## Phase B：独立検証

**verify1 のレポートは読まずに行う。**

### B-1. テストの実行

- 全テストを実行し、失敗をすべて記録する。
- スナップショットの更新、自動修正、失敗の許容などのオプションは使わない。
- 失敗は CRITICAL。変更と無関係に見える失敗には「既存の失敗の可能性」と付記する。重大度は下げない。
- 正本の `must` 規約の判定方法が全テストに含まれていない場合は、そのコマンドを個別に実行する。失敗は CRITICAL とし、規約 ID を付ける。

### B-2. 要件とシナリオの挙動

- 差分 spec の各要件（`### Requirement:`）について、実装しているコードを特定して読み、挙動を追う。
- 各シナリオ（`#### Scenario:`）について、条件から結果までの実行経路をたどり、spec の期待どおりの結果になるかを確かめる。
- spec が触れている境界条件、およびシナリオから当然に派生する境界条件（空、最大、不正入力、失敗時、同時実行など）を確認する。
- spec に書かれていないエッジケースの問題は WARNING にとどめる。

### B-3. テストの実質性

- 各シナリオに対応するテストが、そのシナリオの期待結果を実際に検証しているかを確認する。
  - アサーションがあるか、その内容がシナリオの期待結果と一致するか
  - 検証対象そのものをモックやスタブで置き換えていないか
- 差分の中でテストが弱められていないかを確認する。
  - テストの削除
  - skip / only / xfail などの追加
  - アサーションの削除や緩和
  - 期待値を実装の出力に合わせた書き換え
- 差分の中で規約の検査が弱められていないかを確認する（規約正本がある場合）。
  - 検査の許可表・例外リスト・除外パターンの拡大
  - 正本の規約の削除、強度の引き下げ（`must` から `should` / `info` へ）、例外の追加
  - 検査が参照する規約 ID の削除
- 成果物で理由が説明されていないテストの弱体化と規約検査の弱体化は CRITICAL。
  - 違反を解消する代わりに許可表や例外を広げた変更は、design に理由が書かれていなければ、この区分に当たる。

### B-4. 逆方向の検査（diff → spec）

- 差分の各変更を、対応する要件・タスク・設計判断に紐づける。
- 紐づかない変更を列挙する。
  - 挙動を変えるもの：CRITICAL
  - 挙動を変えないもの（整形、無関係なリファクタ）：WARNING
- 依存関係の追加・更新で、成果物に記載がないもの：WARNING 以上
- 継ぎ目に当たる変更は、B-7 で扱う。

### B-5. 設計判断と横断的な観点

- design.md があれば、主要な判断（Decision / Approach / Architecture などの節）を抽出し、実装が従っているかを確かめる。
- 変更に関係する範囲で、次の観点を確認する。
  - エラー処理、入力検証、資源の解放、並行性、セキュリティ、性能、後方互換性とデータ移行
- 具体的な破綻経路（どの入力・状態で何が起きるか）を示せるものは CRITICAL。示せないものは WARNING に `[要確認]` を付ける。

### B-6. タスクの完了

- tasks のチェックボックスを数える。
- 未完了のタスクは CRITICAL。
- チェック済みでも実装が見つからないタスクも CRITICAL。

### B-7. 抽象化と重複

**継ぎ目**とは、呼び出し側と実装の間に新しく置かれ、以後の変更がそこを通るようになる構造をいう。次を含む。
- 新しいディレクトリ・モジュール・パッケージの境界、基点コミットに無かった向きの依存
- 新しく公開する interface・抽象型・基底クラス（`extends`）・公開 API の型パラメータ
- 新しい拡張点（登録 API、プラグイン、イベントの購読、設定による実装の切り替え）
- 新しい外部依存（パッケージ、外部サービス）
- フォークで開発している場合は、フォーク元のコードへの変更

既存の継ぎ目に実装を1つ足すだけの変更は含めない。

1. **継ぎ目の実測**
   - 差分から、追加された継ぎ目をすべて列挙する。
   - 確認する箇所: 新規に export された interface・抽象型・クラス、`extends`、新規ディレクトリ、依存定義（package.json など）の追加、登録 API の呼び出し、基点コミットに無かったモジュール間の import。型のみの import も依存として数える。
2. **設計判断との照合**（Phase A-7 の一覧と突き合わせる）
   - 対応する Decision が無い継ぎ目は SPEC とする。人間が承認していない継ぎ目なので、design に追記して残すか、取り除くかを利用者が決める。
   - Decision はあるが実装の形が違うもの（Decision は既存構造の拡張なのに、実装は新しい interface を追加している、など）も SPEC とする。
   - Decision で計画された継ぎ目が実装されていないものは WARNING とし、design の更新を推奨する。
3. **対価の実現**
   - Decision が対価として挙げたもの（解消する重複、減る変更箇所、複数の実装）が、実装で実現しているかを確かめる。
   - 次は WARNING とする。
     - 実装が1つしかない interface・抽象型
     - 呼び出し側が1つしかない拡張点
     - 1種類の値しか渡されない型パラメータ・オプション
     - Decision が解消すると書いた重複が残っているもの
   - ただし、spec の要求が複数の実装や呼び出し側を求めている場合は除く。
4. **重複の実測**
   - 差分で追加されたコードが、既存コードまたは同じ差分の別の箇所と、同じ処理や同じ知識（定数、設定値、規約本文）を持っていないかを確かめる。
   - 重複検出の手段がリポジトリにあれば（正本の判定方法、package.json の scripts など）それを使う。無ければ、追加された関数ごとに名前と主要な識別子で既存コードを検索し、本文を比べる。
   - 新たな重複は WARNING。片方だけを直すと挙動が食い違う具体的な経路を示せるものは、B-5 と同じく CRITICAL。
   - 規約本文が検査・AGENTS.md・README などに写されている場合は WARNING とし、規約 ID による参照への置き換えを推奨する。
5. **規約との照合**（規約正本がある場合）
   - 追加された依存・継ぎ目が、正本の規約に反していないかを確かめる。
   - `must` 規約に反するもので B-1 の検査が検出しなかったものは、CRITICAL とし、検査の不足を SPEC として併記する。
   - `should` 規約に反するものは WARNING。

## Phase C：verify1 との突き合わせ

verify1 のレポートが渡されていれば、ここで初めて読む。渡されていなければ省略し、レポートにその旨を書く。

- verify1 だけが指摘した項目：再検証し、採否と理由を記す。
- verify2 だけが指摘した項目：verify1 が拾えなかった理由が推定できれば、一行で記す（キーワード一致による実装済みの誤判定、など）。verify1 の調整に使う。
- 重大度が食い違う項目：verify2 の判断を採り、理由を記す。

## 再検証モード

前回の verify2 レポートが渡された場合に使う。

1. Phase A を行う。
2. B-1（全テストと `must` 規約の検査の実行）を行う。
3. 前回の CRITICAL・WARNING・SPEC を一件ずつ再検証し、解消・未解消・悪化のいずれかを記す。
4. 前回レポートに記録した HEAD からの差分（`git diff <前回の HEAD>` と未追跡ファイル）で変わったファイルについて、B-2〜B-7 を行う。
   - 前回の検証が未コミット状態で行われていた場合は、差分の範囲を確定できないので、全体を検証し直す。
5. 対象外の部分は前回の結論を引き継ぎ、そう明記する。

## 重大度

**CRITICAL**（archive 前に必ず修正）
- テストの失敗、`must` 規約の検査の失敗
- 要件・シナリオの意図からの乖離
- 未完了のタスク、実装が見つからない完了済みタスク
- 成果物で説明されていないテストの弱体化と規約検査の弱体化
- 挙動を変える spec 外の変更
- 具体的な破綻経路を示せる横断的な問題（片方だけ直すと食い違う重複を含む）
- 検査が検出しなかった `must` 規約の違反

**WARNING**（修正を推奨）
- シナリオに対応するテストがない、またはテストが期待結果を検証していない（挙動自体は正しい）
- 挙動を変えない spec 外の変更、記載のない依存関係の追加
- 設計判断からの逸脱で、挙動上の問題を示せないもの（計画された継ぎ目が実装されていないものを含む）
- spec に書かれていないエッジケースの問題
- 対価が実現していない継ぎ目、新たな重複、規約本文の複製、`should` 規約の違反

**SUGGESTION**
- 上記以外の改善案

**SPEC**（成果物の側を直すべき問題。人間の判断が要る）
- spec・design・tasks の矛盾、欠落、曖昧さ
- 実装のほうが妥当で、spec を改めるべきと考えられる箇所
- design に Decision が無い継ぎ目、Decision と形が違う継ぎ目
- `must` 規約の違反を検出できなかった検査の不足

**`[要確認]`**
- 根拠が足りない指摘に付ける。重大度は下げない。
- 決着に必要な確認（実行すべきテスト、読むべきファイル、利用者への質問）を併記する。
- `[要確認]` 付きの CRITICAL も、判定では CRITICAL として数える。

## 判定

- **FAIL**：CRITICAL が1件以上ある
- **BLOCKED**：SPEC が1件以上ある（FAIL と併記できる）
- **PASS WITH WARNINGS**：CRITICAL と SPEC がなく、WARNING がある
- **PASS**：いずれもない

archive に進めるのは PASS と PASS WITH WARNINGS のときだけ。verify1 の「Ready for archive」は参考扱いとする。

## 出力形式

```markdown
## Deep Verification Report: <change-name>

- 検証対象: <基点コミット>..<HEAD のコミット>（未コミット変更: あり / なし）
- テストコマンド: <command>
- 規約正本: <path / なし>（基点からの変更: あり / なし）
- verify1 レポート: <path / なし>
- モード: 通常 / 再検証（前回レポート: <path>）

### 判定
<FAIL / BLOCKED / PASS WITH WARNINGS / PASS>

### 集計
| 観点 | 結果 |
|---|---|
| テスト | 成功 X / 失敗 Y |
| 規約検査 | 成功 X / 失敗 Y（正本なしの場合は「省略」） |
| 要件 | 意図どおり M / 全 N |
| シナリオ | 挙動を確認 P / 全 Q、テストが実質的 R / 全 Q |
| spec 外の変更 | 挙動変化あり A 件 / なし B 件 |
| 継ぎ目 | 追加 N 件（Decision あり M / なし K）、対価が未実現 J 件 |
| 重複 | 新たな重複 D 件 |
| タスク | 完了 X / 全 Y |

### 継ぎ目一覧
| # | 継ぎ目 | 種別 | 場所 | 対応する Decision | 関係する規約 ID | 指摘 |
|---|---|---|---|---|---|---|
| N-1 | … | 境界 / 抽象型 / 拡張点 / 外部依存 / フォーク元変更 | `path/to/file.ts:12` | 見出し名 または「なし」 | … または「なし」 | 指摘 ID または「なし」 |

（追加された継ぎ目が無ければ「なし」）

### 指摘

#### CRITICAL
- **[C-1] <要約>**
  - 場所: `path/to/file.ts:123`
  - 根拠: <コードの挙動、テストの出力、該当する要件・シナリオ名、規約 ID、継ぎ目の N 番号>
  - 修正先: 実装 / spec
  - 推奨: <具体的な修正内容>
  - 要確認: <該当する場合のみ。決着に必要な確認>

#### WARNING
（同じ形式、ID は W-1, W-2, ...）

#### SPEC
（同じ形式、ID は S-1, S-2, ...）
継ぎ目に関する SPEC では、推奨に「design に追記して残す」と「取り除く」の両方の場合の作業を書く。

#### SUGGESTION
（同じ形式、ID は G-1, G-2, ...）

### verify1 との突き合わせ
（Phase C の結果。省略した場合はその旨）

### 次の手順
- FAIL：CRITICAL を apply で修正し、このスキルを再検証モードで実行する
- BLOCKED：SPEC の各項目について利用者の判断を仰ぐ
- PASS / PASS WITH WARNINGS：archive に進める
```

すべての指摘に、具体的な場所（`file:line`）と具体的な推奨を付ける。「見直しを検討」のような曖昧な推奨は書かない。
