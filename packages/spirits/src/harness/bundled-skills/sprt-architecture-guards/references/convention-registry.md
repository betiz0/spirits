# 規約正本の書式

規約の本文を持つ唯一のファイルの書式。手順 6 で作る。

## 置き場所

対象リポジトリの 1 ファイルに固定する。既定は `docs/architecture/convention-registry.md` とし、既存のドキュメント構成に合わせて変更してよい。決めたパスは OpenSpec rules と検査から参照する。

## 各規約のフィールド

各規約は次の 6 つを持つ。すべて必須。

| フィールド | 内容 |
|---|---|
| 規約 ID | 安定した識別子。`AG-` と連番(`AG-001`)。並べ替えや削除で再利用しない |
| 強度 | `must`(違反は CI で失敗) / `should`(レビューで指摘) / `info`(記録のみ) のいずれか |
| 内容 | 守ることを 1〜2 文で。実測した対象と依存の向きを具体的に書く |
| 例外 | 適用しない条件と、その理由。無い場合は「無し」 |
| 判定方法 | 検査コマンドまたはレビュー時の確認手順。`must` は実行可能なコマンドを持つ |
| 根拠 | 導入前の計測値、実測で見つかった問題、決定の経緯 |

## 書式の例

```markdown
### AG-001: repl は harness を import しない

- 強度: must
- 内容: `src/repl/` から `src/harness/` への値の依存を禁止する。型のみの import も含む。
- 例外: 無し。
- 判定方法: `bun test test/architecture/dependency-direction.test.ts`
- 根拠: 導入前の計測で `src/repl/` → `src/harness/` の値依存が 2 件。フェーズ分離の担保が目的。
```

## 運用規則

- 規約本文(内容・例外・根拠)を書くのは本ファイルだけ。検査、OpenSpec rules、AGENTS.md、README は規約 ID で参照する。
- 規約の追加・変更・削除は本ファイルを編集してから検査を合わせる。検査を先に変えない。
- `must` の規約は対応する検査コマンドを持ち、CI で実行される。
- 強度を `should` に下げるときは、機械判定できない理由を判定方法に書く。
- 導入前のベースラインと導入後の計測手順を根拠に書き、`references/principles.md` の考え方に沿って比較する。
