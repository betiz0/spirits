# architecture-guards

利用者が `/skill:architecture-guards` で明示起動したときだけ実行する。モデルの自動選択では使わない。

対象は TypeScript を使うリポジトリ。規約はリポジトリの実測から導き、一般論やパターン名を外部から持ち込まない。生成物はすべて差分として提示し、利用者が承認するまでファイルを書き込まない。

詳細は起動時に全部読まず、必要な段階で `references/` を読む。paths はこのスキルのディレクトリ(SKILL.md の親)基準で解決する。

- 規約をどう考えるか: `references/principles.md`
- 規約正本の書式: `references/convention-registry.md`
- 検査の生成方法: `references/check-generation.md`

## 0. 対象判定(手順の前に必ず行う)

1. カレントリポジトリに `tsconfig.json` があるか、`.ts` / `.tsx` のソースがあるかを確認する。
2. どちらも無い場合: 対象外である旨と、TypeScript を使うリポジトリでのみ動くことを伝え、**いかなるファイルも作成・変更せずに終了する**。
3. 判断できない場合(例: `tsconfig.json` は無いが `.ts` が vendored ディレクトリにだけある、対象ディレクトリが複数ありどれを規約の対象にするか決められない): 利用者に質問する。回答が得られないまま終了する場合も、いかなるファイルも作成・変更しない。

## 1. スタック検出

次の項目を検出し、結果を提示する。未検出の項目は「無し」と明示する。推測で補わない。

- 言語とソースの範囲(`tsconfig.json` の `include`、`.ts` / `.tsx` の位置)
- テストランナー(`package.json` の `scripts.test` と依存、設定ファイル)
- linter / formatter(設定ファイルと依存)
- CI(ワークフロー定義の有無と、テストを実行しているジョブ)
- OpenSpec の有無(`openspec/` ディレクトリと `openspec/config.yaml`)
- AGENTS.md の有無(ルートと対象ディレクトリ)

検出結果は以降の原案と生成物に反映する。とくに、検査は検出したテストランナーで実行できる形式にする。

## 2. import 依存の実測と許可表原案の確認

実際の import 依存を、型のみの import(`import type`)を含めて列挙する。ディレクトリまたはモジュールの層にまとめ、依存方向の許可表の原案を作る。

- 実測に現れない依存を許可表に追加しない。
- 循環依存が実測にある場合は、規約で禁止する前に利用者へ確認する。
- 型のみの import は「値の依存」と区別して記録する。判定は TypeScript の AST を使う(`references/check-generation.md` に理由と方法)。

原案を提示し、層の分け方と許可する向きについて利用者の確認を得る。確認が取れるまで次の手順に進まない。

## 3. 重複と継承の計測

規約原案に反映するため、現状を計測して提示する。

- 重複: 同一または酷似したコード片の数と位置、重複した設定値。
- 継承: 継承関係の辺の数、深さ、多段継承の有無。

数値はベースラインとして記録する。規約の強度(CI で強制するか、レビューで見るか)は計測結果と利用者の判断で決める。実測に現れない GoF パターン名や「継承は○段まで」のような一般則を原案に含めない。

## 4. 利用者のテストランナーで動く検査の生成

手順 1 で検出したテストランナーで実行できる検査を生成する。検査は次を満たすこと。

- 利用者の `package.json` の test スクリプト、または同じランナーのコマンドから実行できる。
- 規約違反があれば非ゼロ終了し、違反した規約 ID と場所を出力する。
- 検査の実行に spirits のバイナリ、インストール、spirits 固有のコマンドを必要としない。
- 規約本文を持たず、正本の規約 ID を参照する。

生成方法の詳細は `references/check-generation.md` に従う。

## 5. OpenSpec rules への追記案

対象リポジトリが OpenSpec を使っている場合(`openspec/config.yaml` がある場合)、その rules への追記案を差分として提示する。

OpenSpec を使っていない場合は、`openspec/config.yaml` を作成しない。使っていない旨を伝え、この手順を飛ばす。

## 6. 規約正本

確定した規約を 1 か所の正本にまとめる。各規約は規約 ID、強度、内容、例外、判定方法、根拠を持つ。書式は `references/convention-registry.md` に従う。

規約本文を正本以外のファイル(検査、README、OpenSpec rules、AGENTS.md など)へ重複して書かない。他のファイルは正本の規約 ID を参照する。

## 7. 差分提示と承認後の書き込み

生成物をすべて差分として提示する。提示段階ではまだ書き込まない。

- 承認前に `git status --porcelain` を確認し、リポジトリが変わっていないことを示す。
- 利用者が承認したら、提示した差分と同じ内容だけを書き込む。
- 承認しない場合は何も書き込まず、中止した旨を伝える。
- 承認後に検査を一度実行し、ベースラインで通ることを確認する。違反が出た場合は規約と実測のどちらが誤っているかを確認する。
- 再生成する場合(生成物を削除した後の再実行など)も、git 履歴や以前の生成物を参照せず、手順 2・3 の実測と確定した規約から書き起こす。
