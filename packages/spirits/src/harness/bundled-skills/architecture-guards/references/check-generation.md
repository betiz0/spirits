# 検査の生成方法

手順 4 で生成する検査の技術的な指針。検査は利用者のリポジトリで完結し、spirits に依存しない。

## 対象判定の詳細

手順 0 の判定を、生成する検査にも同じ意味で埋め込まない。検査は対象リポジトリのファイル構成に合わせて生成する。判定の材料は次の順に使う。

1. `tsconfig.json` の `include` / `exclude` と `compilerOptions.paths`。ここに載る範囲を検査対象にする。
2. `src/` など実在するソースディレクトリ。`tsconfig.json` が無い場合は `.ts` / `.tsx` の位置から推定する。
3. `node_modules`、生成物、vendored ディレクトリは除外する。

対象ディレクトリが複数あり、どれを規約の対象にするか決められない場合は、検査を生成する前に利用者へ質問する。

## 依存方向検査

規約正本の許可表を入力に、リポジトリ内の import が許可された向きだけであることを検査する。検査対象は型のみの import を含むすべての import とし、値の依存と型のみの依存を区別して許可表と照合する。許可の有無が値と型のみで異なる場合は、それぞれの辺を別に判定する。

1. 対象の `.ts` / `.tsx` を列挙する。
2. 各ファイルをパースし、`ImportDeclaration`、`ExportDeclaration`、`ImportEqualsDeclaration` を走査する。
3. 各 import を、リポジトリ内の解決済みパスへ変換する(`tsconfig.json` の `paths` と相対解決を使う)。
4. 層(ディレクトリ)間の依存辺に変換し、許可表と照合する。
5. 許可されていない辺があれば、規約 ID と import 元・先を出力して非ゼロ終了する。

### 型のみの import を AST で判定する理由

- 規約では値の依存と型のみの依存を区別する。`import type { T }` と `import { type T, f }` を正しく分ける必要がある。
- `Bun.Transpiler#scanImports` は使わない。Bun 1.4.2 で確認したところ、`import type` だけの文は結果に現れず、混在文でも型のみの specifier を区別できない。型のみの依存を含める規約が判定できない。
- TypeScript の AST(`ts.createSourceFile` + `forEachChild`)を使い、`ImportDeclaration.importClause.isTypeOnly` と各 `ImportSpecifier.isTypeOnly` を読む。TypeScript は対象リポジトリの既存依存にあるものをそのまま使う。無ければ検査を生成する前に追加の可否を利用者へ確認する。
- 検査コードに `typescript` 以外の新しい依存を持ち込まない。

### TypeScript のバージョンと API の選択

検査は、対象リポジトリにインストール済みの TypeScript で動く API を選ぶ。

- TypeScript 5.x 系: ルートの `typescript` から `ts.createSourceFile`、`ts.isImportDeclaration`、`ImportClause.isTypeOnly`、`ImportSpecifier.isTypeOnly` を使う。
- TypeScript 7.x 系(ネイティブ実装): ルートの `typescript` は classic API を公開しない。`typescript/unstable/async` の `API` / `Project` / `Snapshot` と `typescript/unstable/ast` の `SyntaxKind`・ノード型を使う。`ImportType` の `argument` など一部の箇所は `as unknown as` を経由したアサーションが必要になる。
- どちらか判断できない場合は、`node_modules/typescript/package.json` の `version` を読み、生成前に `bun -e` などで API の存在を実測してから検査を書く。

### 循環の判定

値の import だけからなるファイル依存グラフが非循環であることを検査する。

- 型のみの import の辺は方向の許可表には含めるが、循環判定からは除外する。
- 型のみの辺を含む混合循環は実測のベースラインとして記録する。値の循環が 0 件であることを確認する。
- 循環が見つかった場合は、規約にする前に利用者へ確認し、修正するかベースラインとして許容するかを決める。

## 重複と継承の計測

`must` の規約にする前に、ベースラインを計測する。計測結果は正本の根拠に書く。

- 重複: 正規化した関数本体と定数定義のハッシュを作り、同じハッシュを持つ箇所を列挙する。しきい値(行数など)は実測の分布から決める。
- 継承: `extends` / `implements` の辺を数え、深さの最大値と多段継承の有無を出す。
- いずれも違反そのものではない。しきい値を規約にする場合は、実測で問題が確認できた場合だけにし、値と根拠を正本に書く。

計測は検査としても再実行できる形で生成する。導入前後の比較(`references/principles.md` の 4 番目)に使う。

## 検査の実行形式

利用者のテストランナーで実行できる形にする。

- `bun test` / `vitest` / `jest` など、手順 1 で検出したランナーのテストファイルとして置く。
- または `package.json` の `scripts.test` から呼ばれるスクリプトとして置く。この場合も追加のランナーを要求しない。
- 失敗時は違反した規約 ID と場所を標準出力に出し、非ゼロで終了する。
- spirits のバイナリ、インストール、spirits 固有のコマンド、`tsrepl` を検査から参照しない。

### CI が無いリポジトリ

CI ワークフローが無い場合でも、機械判定できる規約は `must` にしてよい。ただし CI ワークフローを勝手に新設しない。

- 判定方法には `bun test` などの実行可能なコマンドを書く。
- CI への組み込みは `info` の規約として記録し、CI 導入時に実行されることを確認する。
- 検出結果(CI が無いこと)を正本の根拠に残す。

## 再実行と冪等性

同じ入力から生成をやり直す場合(生成物を削除した後など)、git 履歴や以前の生成物を参照してはいけない。手順 2・3 の実測と確定済みの規約から書き起こす。

- 2 回目の生成物は、ファイル構成・規約 ID・検査名が 1 回目と一致していることを確認する。
- 検査のベースライン(成功/失敗と対象件数)が一致することを確認する。
- 文章表現や表の細部は生成のたびに同一にならない。バイト単位の一致を要求しない。

## OpenSpec rules への追記案

対象リポジトリが OpenSpec を使っている場合は、`openspec/config.yaml` の `rules` へ次を追記する案を差分で提示する。

- 規約正本のパスと、そこが正本であること。
- 規約の変更時は正本と検査を同じ変更で更新すること。
- `must` の規約に対応する検査コマンド。

OpenSpec を使っていない場合は、`openspec/config.yaml` を作成しない。追記案も出さず、使っていない旨を伝える。

## 差分の提示

生成するファイルは、パスと内容の差分として提示する。検査の実行コマンドと、ベースラインで通ることの確認結果を添える。承認前にファイルを書き込まない。
