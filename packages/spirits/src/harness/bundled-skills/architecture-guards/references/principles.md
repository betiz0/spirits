# 規約をどう考えるか

手順の背後にある考え方。判断に迷ったときに読む。

## 1. 統制対象は抽象化の追加と重複の蓄積の両方向

規約が防ぐべき失敗は 2 種類ある。

- 抽象化の追加: 実測にない層・interface・基底クラス・パターンを持ち込み、依存が読みにくくなる。
- 重複の蓄積: 同じ知識が複数の場所に写され、片方だけ直る。

片方だけを規約にすると、もう片方が増える。たとえば「継承を禁止」だけを置くとコピペが増え、「共通化を必須」だけを置くと過剰な抽象化が増える。

計測では両方を数える。抽象化の側は層の数・依存辺の数・新しい継ぎ目の数、重複の側は同一コード片と重複した設定値の数を見る。規約は、実測で確認した方向にだけ置く。

## 2. 機械判定できる規約は CI で強制し、人間のレビューは新しい継ぎ目に絞る

規約の強度は、次の順で決める。

1. 判定方法が機械的で、例外が少ない → 検査を生成し、利用者のテストランナーと CI で強制する。
2. 機械的に判定しにくい、または例外が多い → レビュー項目にし、判断の材料(規約 ID と例)を正本に置く。

人間のレビューは、新しい継ぎ目を増やす変更に絞る。具体的には、新しい層・新しい interface・新しい外部依存・新しいディレクトリ境界を追加する変更である。この種の変更は、規約の許可表そのものを変えるため、CI では検出できない。

すべてをレビューに回すと、形骸化して通りやすい変更だけが指摘される。まず機械化できるものを検査に落とし、残りをレビューに残す。

## 3. 規約本文は正本 1 か所

規約本文(何を守るか、例外は何か、なぜか)を書く場所は 1 つに決める。`references/convention-registry.md` の書式で作った正本だけが本文を持つ。

検査、OpenSpec rules、AGENTS.md、README は正本の規約 ID を参照する。参照だけにしておくと、規約の変更は正本の編集 1 か所で完結し、写しの取り違えが起きない。

検査コードに規約文をコピーしない。検査が出力するのは規約 ID と違反箇所にする。

## 4. 導入前後で成果指標を比較する

規約の導入時に、比較できるベースラインを残す。

- 導入前に計測した値(重複数、依存辺数、継承の深さ、新しい継ぎ目を増やす変更のレビュー時間など)。
- 導入後に同じ手順で計測した値。

導入後しばらくして指標が悪化していたら、規約の強度か対象が合っていない可能性がある。規約自体を見直す材料にする。指標が動かない規約は、検査かレビューのどちらかに無駄があるシグナルとして扱う。

ベースラインの値は正本の各規約の根拠に記録する。
