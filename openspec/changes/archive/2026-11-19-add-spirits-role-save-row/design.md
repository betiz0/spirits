# Design

## Context

動機は `proposal.md`、managed 経路の前提は `docs/spirits-design.md` §4.5・§4.7 と `docs/spirits-managed-pi-design.md` §§2–3 を参照。

- Pi 1.5.0 の公式 artifact を隔離 agent dir で動かすと、`/model` の通常選択は global settings を変更しない。`spirits/auto` を既定にした新規セッションでは、利用できる `models.normal` があれば normal の要求が通り、指定を消すと履歴がない最初の normal の要求が失敗する。
- 以下は同じ固定版の配布コードで確認した（実装から内部ファイルを import しない）。`pi-tui/dist/components/settings-list.js` の `handleInput` と `handleMouse` は Enter/Space/クリックを `activateItem` に渡す。候補なし・値なしの行は選択できるが何もしない。`pi-coding-agent/dist/main.js` の `buildSessionOptions` は明示指定を優先し、スコープ外の既定値は選ばない。`dist/core/agent-session.js` の `setModel` は Pi の既定保存時にスコープも補う場合がある。
- 同版の `dist/core/settings-manager.js` では `getSettings()` と再読み込み後の値は global と信頼済み project のマージ結果。`dist/modes/rpc/rpc-mode.js` は `notify` をイベントとして送り、`dist/modes/print-mode.js` は UI を bind しないため `dist/core/extensions/runner.js` の無操作の `notify` になる。実際の `save` に対する確認は tasks の統合検証で行う。

## Goals / Non-Goals

**Goals:** 一覧とコマンドで同じ保存を行い、既定値とセッションの実効状態を混同しない。新規セッションが旧既定や履歴に依存して壊れる保存を防ぐ。一覧の操作行でロックと既定保存を 1 Enter で行い、結果は閉じた後も通知で読めるようにする。

**Non-Goals:** Pi のモデル選択・既定保存の代替、`enabledModels`・thinking・ステップ設定・`models.normal` の自動変更、セッション記録への追記、保存の undo や履歴、`status` への保存日時・内容の追加。

## Decisions

### 1. 一覧アダプターで Enter を識別する（Q-4）

`role-panel.ts` の `openRolePanel` 内で、`SettingsList` の公開 `Component` 境界を通して入力を委譲する。`save` と `use normal` / `use strong` の行だけ単一の `values` を使い、`onChange` をその行の起点とする。操作を呼ぶのは公開 `matchesKey` が Enter と識別したキーを、リストが確定入力として同期処理している間だけ。Space・他の確定キー・マウスが同じ `onChange` を起こしても何もしない。`use` の行はロックの書き込み(`/spirits-role <role>` と同じ)を先に行い、その後に保存を行う。ロックと保存の両方が成立したとき、またはロックが成立して保存に差分が無いときに閉じる。通常行への入力・マウス操作は従来どおり委譲し、`capturesViewportInput` も維持する。Pi の確定キーを Enter 以外に変更している場合は、操作行を他のキーに割り当てず、コマンドを利用できることを文書に残す。`SettingsList` が値を先に更新するため、作動しない入力、失敗、再描画エラーでも操作行の右欄は空のままにする。ホストの非公開メソッドには触れない。

- **追加しない案:** 既存 submenu の選択経路だけを使う。入力の識別が不要だが、候補を開かない1 Enter の要求を満たさない。`onChange` を直接使う案も Space とクリックで即時保存するため不採用。
- **対価:** `openRolePanel` に入力元を区別する局所的な処理が増える代わりに、通常行の入力処理・スクロール・Esc を書き直さず、`save` だけを Enter に限定できる。
- **撤回条件:** Pi の公開 API が入力を限定できるアクション行を提供したら委譲処理と単一値 workaround を撤去する。固定版の更新で同期 callback の検証が落ちたら、移行先の公開 API で契約を再確認するまで採用しない。

### 2. 区行は設定操作なしの行とする

ラベル・値・説明を空にし、`values` も `submenu` も渡さない。カーソルやスクロールは通常どおり動くが、区行は候補・書き込み・再読み込みを起こさない。通常の設定行だけがルーティングの解決を説明する。操作行の説明は予告(`use` の行はロックするロールと `save` の予告)とし、一覧を閉じずに残る失敗のときだけ結果の理由を出す（振り分け無効時は現モデルを先頭に1回示す）。区行には説明を置かない。

- **代替案:** 説明に改行を入れる。説明は選択中の行にしか出ず、一覧の区切りにならない。

### 3. `spirits/auto` の保存は書き込み後の global 値・履歴なしで判定する（Q-2）

保存予定の `defaultProvider` / `defaultModel` を global 設定に重ね、セッション履歴を渡さず `routing/resolve.ts` の `resolveNormalTarget` を使う。旧既定の物理モデル、成功応答、project の `models.normal` は保証に使わない。provider を省いた指定も、保存後の既定 provider で解決する。解決できなければモデルの2キーを変更せず、理由と利用可能な `provider/id` を `models.normal` に設定する案内を返す。物理モデルはこの判定の対象外。モデル未選択ならモデルの2キーは変更しない。

利用可否の根拠は global の設定・資格情報・カタログだけで、現在のセッションのカタログではない。project の拡張が登録した provider、project の設定だけが指すモデル、起動時だけ追加されたモデルは、別の project では存在しないため条件を満たさない。ホストは provider の由来表示を公開していないので、登録一覧を取得できない場合は、取得できた空の一覧と区別する。前者ではモデルの2キーを書かない。取得できた場合にも global 所有と確認できない provider は安全側で見送り、ロールだけを保存する。

- **代替案:** 一覧の現在の表示用解決をそのまま再利用する。旧既定や成功履歴にフォールバックし、保存後に最初の normal の要求が解決できなくなるため不採用。`models.normal` の補完も既存ロール設定を変更するため行わない。現在のセッションのカタログをそのまま使う案は、project 専用 provider で別 project の初回要求を壊すため不採用（検証で再現）。
- **保存の範囲:** セッションのロックと選択モデルの3キーのみ。スコープ、明示的なモデル指定、project 上書きの優先順位は変えない。Pi の `Ctrl+S` と同じモデルキーでも、スコープを変更する代替案は副作用が広がるため採らない。
- **対価・撤回条件:** global の利用可否を判別する公開 API が無い間は、判別できない provider の virtual 既定を保存しない（安全側）。ホストが provider の由来表示を公開したら、その値で判定する。
- **型境界:** provider provenance の問い合わせ型は、公開 host 型 `ExtensionModelRegistry["getRegisteredProviderIds"]` から導出する。ARCH-PI-BOUNDARY は host 型の手書きミラーを検査するが、この indexed access の複写は検出しない。正本と検査を変えずに型を導出するため規約側の課題として残す。
- **既知の限界:** 資格情報の由来は判別しない。現在のプロセスだけが持つ環境変数(例: `ANTHROPIC_API_KEY=… spirits` で保存し、変数無しで起動する)でも `hasConfiguredAuth` は真になるため、その保存は成立し得る。ホストが資格情報の由来を公開するか、`models.normal` の解決を `auth.json` と `models.json` の `apiKey` に限る API を提供したら、その値で判定する。

### 4. 保存するロールは位相のロックであり、記録は追加しない

ロールの取得はロック行と同じ `phase.lock()`。`save` はステップを終了せず、セッションのモデル・thinking・ロックを変更せず、`spirits_role` を追記しない。`status` は今の実効状態を報告し続ける。`use` の行はこの限りではなく、意図してセッションのロックを変える（Decision 12）。

- **代替案:** ステップのロールを保存、または既存のロック設定操作を呼んで保存する。前者は一時的な値を既定にし、後者はステップ終了やセッション記録の追記を伴うため不採用。

### 5. プレビューは global の現在値、確定はロック下の現在値で比較する（Q-1）

一覧は既存の `globalSettingsPath` と `readSettingsFile` で global の予告を組み立てる。保存確定時は `settings-store.ts` の既存ロック・マージ経路の中でディスクの現在値を読み、差分と Decision 3 の安全条件を再判定する。比較は `defaultProvider` / `defaultModel` について Pi がファイルから読む生の値で行い、`readRoutingSettings` の trim 済み値と混ぜない。`models.role` は Pi ではなく spirits が読むため、spirits の読み取りと同じ正規化(前後の空白の除去と小文字化)で比較する。`defaultProvider` / `defaultModel` は Pi がそのままモデル検索に使うため、前後の空白を含む値は差分として扱い、正規の選択値で書き直す。global の対象キーをセッションの値と比較し、書ける差分がなければファイルを再書き込みしない。スキップ理由があるときは、書ける差分がなくても理由を出す。書き込む場合は `models.role` の差分と、変更が必要な既定モデルの2キーを単一パッチで更新する。対象外のキーを保持し、保存結果はこの書き込みで確定した global 値に基づく。

設定ファイルが存在しないときも、同じパスのファイルロックを先に取得し、ロック下で現在の内容を読んでから、書き込む内容があるときだけ作成する。存在確認とロック取得の間に別プロセスが作った内容を空の設定で上書きしない。ロックを取得できなかったときはファイルを作らない。Pi 自身も存在するファイルだけをロックするが、spirits は作成も自分の書き込みとして行うため、作成をロックの外に出さない。

- **代替案:** `pi.getSettings()` やプレビューの比較だけで書く。project の上書きや別プロセスの変更で誤判定する。preview と commit で別の判定式を持つ案も採らない。
- **代替案:** ファイルが無いときは先に `{}` を作ってからロックする。ロック取得に失敗してもファイルが残り、別プロセスの初回保存を空の設定で上書きし得るため不採用（検証で再現）。
- **対価・撤回条件:** 既存ストアに条件付きパッチの入口が増える代わりに、保存専用のロック取得・JSON 書き出しを作らず、比較と書き込みの間の競合を防ぐ。プレビューの読取りが失敗した場合は `save` 行に理由を表示し、通常行の編集は妨げない。一覧の予告は `RolePanel` のスナップショット入力で、`register.ts` の `readGlobalSettings` 差し替え口はテストが隔離 agent dir を直接使えないための seam である。本番の既定は `globalSettingsPath()` の実ファイルで、そのことは `SPIRITS_CODING_AGENT_DIR` を一時ディレクトリへ向けたテスト（`the save row previews pi's real global settings file by default`）で固定した。差し替え口が残るのは、1 つのファイルを使い回す多数のプレビューケースを安く書くためであり、ケースごとに agent dir を分けるようになったら外す。ホストに同じ global 比較・パッチを一度に行う公開 API ができれば、条件付きストア入口を置き換える。

登録側の `saveSettings` writer は本番では既存ストアを呼び、テスト時だけ差し替える。実ファイルを事前にロックするだけではロック段階の `models.role` 書き込みまで失敗する。二段目だけを決定的に拒否し、ロック・badge・ディスク・閉じるときの再読み込みを登録経路で検証するため、この入口を残す。同じ部分失敗を隔離ファイルで競合タイミングに依存せず再現できたら、登録側の差し替えを外す。

### 6. 保存処理は `role-write.ts` に一つ置く（Q-3）

一覧とコマンドは `role-write.ts` の同じ保存処理を呼ぶ。予告と確定は同じ判定を使い、確定結果で失敗・変更なし・書き込みありを区別する。既存 `RoleWrite` の単一パスの結果を複数パスへ拡張し、実際に変わったキーだけを返す。既存の通常編集は `applyRoleLock` / `applyRoleSetting` から1件の変更として返し、`RolePanel.edit()` の pending 管理と `register.ts` の設定変更後警告は同じ複数パスの結果を消費する。失敗・変更なしは pending を増やさない。`SettingChange` は両入口が共有するが、`SaveDecision` は `decideSave` の戻り値としてだけ使い、モジュール外へ公開しない。

一覧の予告が「既定モデルの2キーが変わるか」を判定するときは、保存計画の `writes` に `defaultProvider` / `defaultModel` が含まれるかで決め、生値の比較を予告側にもう一度書かない。`save` 行の結果は、`RolePanel.save()` の戻り値をアダプターが先に保持する。一覧を閉じずに残る失敗の理由は、その後の `refresh()` が失敗しても行から失わず、通常行の読取り失敗だけを `not redrawn` として示す。成立した保存と差分なしの結果は一覧を閉じた後に通知で読むため、行の表示に依存しない（Decision 12）。

- **追加しない案:** `register.ts` と `role-panel.ts` が直接、既存ストアへ別々に書き、結果は別々に作る。入力分岐・失敗処理・表示の反映が二重になる。単一パスを増やさず、save 結果を一覧の専用処理だけで反映する案では、その行だけ別の pending 処理になる。
- **追加しない案:** `SaveDecision` を公開 interface にして呼び出し側へ渡す。現時点で別モジュールから参照する利用者がなく、実装が1つしかない抽象になるため不採用。
- **対価:** 保存・通常編集の結果を消費する2箇所を変える代わりに、両入口の書き込みと失敗を共有し、`role-panel.ts` の既存の一覧反映・通常編集の終了時再読み込みの判定に載せる。別モジュールや差し替え用 interface は増やさない。
- **撤回条件:** `save` 自体を取り除くか複数キーの同時反映が不要になった場合、単一パスの結果に戻し、共有計画・条件付き書き込みの専用面を撤去する。

### 7. 保存は再読み込みせず、結果と実効設定を分ける（Q-1・Q-5）

`save` 行はディスク値の変化とスキップ／失敗理由を示す。`save` は**再読み込みしない**。保存するのは次に始まるセッションの既定であり、再読み込みは現在のセッションのロックやステップを project の既定へ戻し得る。記録のないセッションで project の既定 role を外部から変えた場合、保存した global の role と現在のロックが食い違う。物理モデルで始めたセッションの、ルーティングが一度も解決していないステップも、再読み込みで復元されて寿命が変わる。応答中はホストが再読み込みを拒否するため、書き込みだけ成立して再読み込みされない状態も作れる。
`save` と `use` の行は、書き込みが成立したとき、および差分が無いとき（`use` はロックと保存の両方）に一覧を閉じる。書き込みに失敗したとき、および `use` でロックだけが成立して保存が失敗したときは閉じない。閉じる場合も、書き込みの結果とモデルを見送った理由は元の TUI 画面で読めるよう通知し、閉じた画面で読めなくなる情報を増やさない。

一覧が開いている間、通常行の解決に使う既定値はホストの現在の実効値のままにし、global の保存結果で project の上書きを塗りつぶさない。通常の設定変更は従来どおり、コマンドでは書き込み後に、一覧では閉じるときに一括で1回再読み込みする。`use` の行はロックを書く通常の設定変更として扱い、その行が閉じるときの1回に含める。`save` だけが成立した一覧は閉じても再読み込みしない。通常行の既存の即時更新は維持する。

通知は結果の種別に対応させる。書き込みの成立と変更なしは `info`、失敗だけを `error` とする。モデル未選択のセッションを物理モデルの選択として扱わず、振り分け無効の警告を出さない。TUI と RPC は通知し、print は保存だけして通知しない。一覧を閉じる場合は、reload の前に捕捉した UI オブジェクト(`ctx.ui`)へ reload の後に通知する。reload は transcript を消し、`ctx` を無効化するため、reload の前の通知は読み手に届かず、reload 後の `ctx.ui` は使えない。stale なコンテキストは触らない。`save` が失敗しても、それ以前の通常編集が成功していれば閉じるときの再読み込みは取り消さない。

- **代替案:** 保存のたびに `ctx.waitForIdle()` を待ってから再読み込みする。応答中の拒否は避けられるが、再読み込みが project の既定を読み直して現在のロック・ステップを変える問題は残る。保存前にセッション記録を追記してロックとステップを固定する案は、`save` が記録を変えないという要件に反するため不採用。
- **代替案:** `save` の結果を通知だけで伝え、一覧に失敗の理由も残さない。失敗して開いたままの一覧で理由が読めず、もう一度操作するまで原因が分からないため不採用。また、成立の結果を行だけに出して閉じる案は、閉じた後に何も確認できなくなるため不採用。
- **対価・撤回条件:** 現在のセッションの実効設定は次の明示的な再読み込みまで古いままになる。その間も `save` の結果は通知と設定ファイルで確認でき、通常行と `status` は実効値を示す。ホストがセッション状態を変えずに設定だけを読み直す API を提供したら、保存後の再読み込みを再検討する。

### 8. コマンド語彙と一覧専用の行 ID を分ける

一覧と文法で共有する `save` は `constants.ts` を正本にする。`use normal` / `use strong` は一覧専用の行で、コマンド語彙にはしない。同じ操作は既存の `/spirits-role <role>`（ロック）と `/spirits-role save`（保存）の連続で行えるため、語彙・補完・使用法に新しい語を増やさない。区行と操作行の ID は一覧内でのみ使う。

- **代替案:** `use` を新しいコマンド語として追加する。一覧の行と文法の語彙が二重になり、`/spirits-role <role>` との違いを説明する必要が増えるため採らない。

### 9. print の引数なしは出力しない

`/spirits-role` の引数なしは、対話 TUI では一覧、RPC では `status` の通知、print では何も出力しない。print はモデルの最終回答を stdout に出す面で、拡張の稼働状況を混ぜると利用者が回答と状態を区別できなくなる。`save` が print で無通知なのと同じ出力契約に揃える。

- **代替案:** print の引数なしで `status` を stdout に書く。`-p` の出力がモデルの回答だけであるという既存の契約を変え、`save` の無出力とも食い違うため不採用。
- **撤回条件:** ホストが print 用の状態出力路を提供したら、`status` をそこへ出す。

### 10. 読めない設定値の診断は解決結果を置き換えない

`roleResolutionLines` は `models.normal` が読めない場合も、解決した応答モデルを `target` に残し、診断を `source` に足す。一覧の行は診断と応答モデルの両方を出す。読めないという事実は「未設定」や「使えない」とは別だが、実際に応答するモデルを隠す理由にはならない。

- **代替案:** 現在のように `target: "unreadable"` にして診断だけを出す。ルーターが Pi の既定モデルで応答しているのに、一覧がどのモデルで答えるかを示さないため不採用（固定版で再現）。

### 11. 使い方と通知の語彙を一か所に揃える

共通の使用法 `USAGE` は `ROLE_SAVE_WORD` を使って `/spirits-role save` を含める。文法の拒否・補完・一覧の行が同じ語彙を指す。通知は `saved` / `nothing to save` を `info`、失敗だけを `error` とし、モデル未選択は物理モデル選択として扱わない。

- **代替案:** `save` の使用法を `save` 固有の拒否文だけに書く。一般の引数誤りから `save` の存在を知る経路がなく、タスク 2.2 の要求を満たさないため不採用。

### 12. 一覧の操作行は `use normal` / `use strong` を最上段に置き、成功で閉じる

行順は `use normal`、`use strong`、`save`、区行、既存行（`role lock`、モデルと thinking、ステップ）。ロックと既定保存を 1 Enter で終える経路を最上段に置き、設定を編集する既存行とは役割を分ける。

既存の `role lock` 行でも normal / strong を選んでロックできる。両方を残すのは、行を読みながら設定を変える経路と、決めた状態に切り替えて一覧を閉じる経路が別の用途だからである。重複した書き込み経路は既存のロック書き込みと共通の保存を呼ぶだけで、3つ目の実装を作らない。

`use` 行の成功はロックと保存の両方が成立したとき、または保存に差分が無いときで、そのときに閉じる。ロックが失敗したとき、ロックだけが成立して保存が失敗したときは閉じず、行に理由を出す。`save` 行も成立・差分なしで閉じ、失敗では閉じない。閉じるときは、reload の前に捕捉した UI へ reload の後に結果を通知する。

- **代替案:** `role lock` 行を `use` 行に置き換える。設定値の編集経路が消え、ロックだけを変える操作ができなくなるため採らない。
- **対価:** 一覧の行が 2 行増え、Enter 限定の操作行が 3 つになる。代わりに、ロックと既定保存を 1 操作で終えられる。
- **応答中の閉じる:** `use` 行は通常の設定変更として閉じるときに再読み込みする。応答中はホストがそれを拒否し得るが、元の画面には「保存済み・再読み込み未完了」と伝える。保存失敗と扱わず、再試行・ロールバックはしない。

## Risks / Trade-offs

- [Risk] Pi 更新で `SettingsList` の入力委譲や callback のタイミングが変わる → Mitigation: 固定版の公開コンポーネントを Enter/Space/クリックで駆動し、版更新時も同じテストを実行する。
- [Risk] プレビュー後に他プロセスが global を更新する → Mitigation: 確定時に読み直して単一パッチを作り、プレビューでなく確定結果を表示する。Pi の既定保存と同じキーへの後続の書き込みは最新の書き込みが優先される。
- [Risk] 保存後に `models.normal`・資格情報が壊れる → Mitigation: 保存時だけ判定する。使用時の失敗は既存の badge・`status` の診断に従う。
- [Risk] project の拡張だけが登録した provider を global の安全条件の根拠にして、別 project の初回要求が失敗する → Mitigation: global の設定・資格情報・カタログだけで解決できないモデルは保存しない（Decision 3）。別 project での起動を回帰テストに含める。
- [Risk] 保存が現在のセッションのロックやステップを変える → Mitigation: `save` は再読み込みしない（Decision 7）。project の既定変更中と、ルーティング未解決のステップ中を実機で確認する。
- [Risk] 空白付きの既定値を Pi が解決できず、保存が「変更なし」になる → Mitigation: 比較を生の値で行い、空白付きの値は正規の選択値で書き直す（Decision 5）。
- [Risk] 保存行の結果が再描画失敗で予告に戻る → Mitigation: 一覧を閉じずに残る失敗では `RolePanel.save()` の結果を先に保持し、失敗の理由を残す（Decision 6・12）。
- [Risk] 一覧を閉じた後に保存結果を読めない → Mitigation: 元の TUI 画面で結果と見送り理由を通知する。RPC は各コマンドの通知を個別に検証する（Decision 12）。
- [Risk] `role lock` 行と `use` 行の二重の経路が実装ごとにぶれる → Mitigation: 同じロック書き込みと共通の保存を呼び、用途の違いを design と文書に記す。
- [Risk] 応答中に `use` 行で閉じたとき、ホストが閉じる再読み込みを拒否する → Mitigation: ロック・保存・通知は完了させ、保存成功とは別に再読み込み拒否を通知する。実効値は次の明示的な再読み込みまで古い場合がある。
- [Risk] `save` が現在のセッションの実効設定を更新しないことを誤解される → Mitigation: 一覧の `save` 行はディスク、通常行と `status` は実効値と文書に書き、再読み込みは通常の設定変更だけが行うと明記する。
