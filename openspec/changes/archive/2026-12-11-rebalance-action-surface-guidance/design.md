# Design

## Context

- 規則の文言は 3 か所から出る。`packages/spirits/src/tools.ts` の `TSREPL_PROMPT_GUIDELINES`(pi が `<rules>` に並べる)、同じ配列をそのまま埋め込む `packages/spirits/src/harness/prompt.ts` の code-mode プロンプト、ガードのブロック理由(`packages/spirits/src/constants.ts` の `GUARD_CATEGORY_GUIDANCE` と `packages/spirits/src/guard/messages.ts`)。pi 既定の "Use bash for file operations like ls, rg, find" はホスト側の文言で変えられない。現行の 3 項目の合計は 356 文字。
- ガードの判定は `packages/spirits/src/guard/rules.ts` の `classify(command, scope, { nested })` に集まっている。字句解析器(`guard/lex.ts`)は、引用符を外した語の値を `LexedWord.text` に、コマンド置換を含むかどうかを `dynamic` に持つ。そのため、シェルの `-c` の引数は `lex()` にそのまま渡し直せる。
- インタプリタの認識は `findInterpreter` が担い、ラッパー `env` / `timeout` / `nice` / `uv run` を読み飛ばす。python の名前は `INTERPRETER_PATTERNS` の `/^python[0-9]*(\.[0-9]*)*$/` が判定している。
- `GUARD_CATEGORY_GUIDANCE` の型は `Record<GuardCategoryId, ...>` なので、分類 ID を足すと、その項目が無い限り型検査が通らない。`guard/register.ts` はハンドラ全体を try/catch で包んでおり、理由の組み立てが例外になると、ブロックせずに実行を通す。
- tsrepl の vm には `process` / `Bun` / `require` を意図的に入れていない(`repl/context.ts` の `ALLOWED_GLOBALS`)。一方、`repl/format.ts` の `suggestFix(name, message)` は、未定義の識別子をすべて「`globalThis` へ代入」と案内している。`rlm` の子セッションには `sh` が無く、bash も呼べない。
- 前回の変更 add-action-surface-guard の design では、シェルの `-c` を範囲外とし、一時ディレクトリの `.ts` は通すと決めた。この変更は前者を覆し、後者は維持する。
- 測定の根拠は proposal の Why に書いた実セッションログ 20 本である。読み取り専用で集計した。

## Goals / Non-Goals

**Goals:**
- モデルが bash を書く前に行き先を決められる文言にする。ブロックされた後も、意図に合った道具へ案内する。
- Python の実行を、名前とシェルの `-c` / `eval` の両方から止める。
- tsrepl の典型的な失敗(`use()` の `await` 漏れ、`process` / `Bun` の参照)を、説明文と提案文で減らす。

**Non-Goals:**
- write / edit ツールでの `*.py` の作成は止めない。
- 実行時に決まるコマンド名(`$PY`)、シェルスクリプトファイルの中身、ラッパー以外のコマンド(`sudo`、`docker`、`ssh`)の引数は判定しない。
- tsrepl の vm に `process` / `Bun` を入れない。
- P2 の判定(一時ディレクトリの `.ts` は通す)は変えない。

## Decisions

### 1. 規則を意図ごとの 4 項目にし、出典は 1 つのままにする
`TSREPL_PROMPT_GUIDELINES` を 4 項目にする。内容は、ファイルの読み書き(read / edit / write)、bash(単発の実行で出力を自分で読む)、tsrepl(出力をコードで扱う処理と使い捨てのコード)、python の禁止。code-mode プロンプトはこれまでどおり、この配列をそのまま埋め込む。bash の項目に並べるフィルタは、今までどおり `BASH_PIPE_ALLOW_FILTERS` から作る。
- 代替案: 3 項目のままにし、read / edit への案内はブロック理由だけに足す。不採用とした。測定では、行き先の誤りはブロックされる前の選択の時点で起きている。事後の案内だけでは、ブロック件数が減らない。

### 2. Python の禁止は新しい分類 P3 にし、P1 / P2 との重なりを許す
P3 はコマンド位置の名前だけで判定し、引用されていても展開なしに確定する名前を含める。引数や動的な名前は対象外とし、他の分類の引用符の扱いは変えない。P3 は P 系に入れ、入れ子の呼び出しにも適用する。`python3 -c` は P1 と P3 の両方に該当し、ブロック理由には 2 行とも出る。
- 代替案: python を P1 / P2 の対象から外し、P3 だけで扱う。不採用とした。既存の要件のシナリオとフィクスチャの多くが python を P1 / P2 の例に使っており、書き換えが大きい。インラインコードという P1 の案内も、Python に対して誤りではない。

### 3. python の名前は 1 か所で定義し、P3 にはツール名の一覧だけを足す
P3 の python 系の判定は、`INTERPRETER_PATTERNS` の python の項目をそのまま参照する。P3 が独自に持つのは、インタプリタではないツール名の一覧(`pip`、`pip3`、`pipx`、`uv`、`uvx`、`pytest`、`poetry`、`hatch`、`pdm`、`tox`、`ipython`、`jupyter`)と、`.py` の接尾辞の判定だけで、`rules.ts` のローカル定数に置く。こうすれば、版付きやパス付きの python 名の表記が変わっても直すのは 1 か所で済む。
- 代替案: P3 に python のパターンを別に持たせる。不採用とした。同じ名前の定義が 2 か所に分かれ、ARCH-DUP は定数の重複を検査しないため、ずれても検出されない。

### 4. ラッパーの読み飛ばしを共通化し、途中で見た名前すべてを P3 で判定する
`findInterpreter` の、ラッパーを読み飛ばす部分を共通化する。P3 は、読み飛ばしの途中で見たコマンド位置の名前(ラッパー名を含む)が Python 系なら該当とする。こうすると、`uv run x` は `uv` 自体で該当し、`env python3 x.py` はラッパーの後ろの名前で該当する。ラッパーに `nohup`(オプションなし)を加える。`sudo` はオプションに値を取るものが多く、読み飛ばしの規則が大きくなるので、ラッパーに加えない(Non-Goals)。
- 代替案: P3 は単純コマンドの最初の語だけを見る。不採用とした。`env` や `timeout` の後ろの `python3` を見逃す。

### 5. シェルの -c と eval は classify の中で分類し直す
`classify` は字句解析の後、解決したコマンド名が `bash` / `sh` / `zsh` / `dash` / `ksh` で、1 文字オプションのまとまりに `c` を含むものを探す。見つかったら、シェル自身のオプションを読み終えた後の語を文字列とする。スクリプト名より後ろや `--` より後ろの `-c` はシェルのオプションではない。`eval` なら、引数を空白でつないだものを文字列とする。どちらも段数を 1 増やして `classify` を再帰的に呼び、結果を和集合にする。`nested` は外側の値を渡す。次の場合は分類し直さない(見逃しの方向)。語が `dynamic` のとき、内側が解析できないとき、4 段目に入るとき。段数は、bash ツールに渡された文字列を 0 段目として数える。外側の引用・エスケープを考慮して変数展開も識別する。既存の `dynamic` だけでは判別できないため、必要な字句情報を保持し、他の分類の適用範囲は広げない。
- 代替案 1: シェルの `-c` を対象外のままにする(前回の決定を維持する)。不採用とした。Python を名前で禁止しても、`bash -c "python3 ..."` で同じことができてしまう。抜け道を探さなくても普通に書かれる形でもある。
- 代替案 2: 字句解析器でシェルの `-c` の中身を展開し、1 つの `LexResult` にまとめる。不採用とした。パイプの段数や制御構文の位置が外側の構造と混ざり、既存の数え方の要件を崩す。
- 撤回条件: タスク 3.3 の再測定で、直接の呼び出しのうち、分類し直しによって新たに S 系に該当した件数を見る。それがガード導入後のブロック件数の 1 割を超え、かつ誤りと判断した事例が半数を超えたら、S 系への適用をやめて P 系だけを分類し直す形に戻す。

### 6. sed の表示だけの判定は、スクリプトを小さく構文解析して行う
`isSedRangePrint` の正規表現 1 本をやめ、スクリプトを左から読む。1 つの表示コマンドは、アドレス、省略できる `,アドレス`、`p` の順に並ぶ。アドレスは 10 進整数、`$`、`/…/` のいずれかで、`/` の中はバックスラッシュのエスケープを解釈する。表示コマンドを `;` で区切って繰り返し、それ以外の文字が出たら不一致とする。`-n` だけ、ファイル名だけ、という条件は今のまま。
- 代替案: `;` で分割してから各片を正規表現で照合する。不採用とした。`/a;b/p` のように、正規表現の中の `;` で誤って分割してしまう。

### 7. ブロック理由は分類ごとに行き先を書く
`GUARD_CATEGORY_GUIDANCE` の書き換え例を行き先別にする。
- S2: 「部分の読み取りは read、書き換えは edit、出力の加工はセル」とし、セルの例を 1 つ付ける。
- S3: write / edit。
- P1: JSON の読み取りのセル例。
- P2: Python を含まないセル例。
- P3: 「Python はプロジェクトの実行を含めどの形でも実行しない」とセル例。

`messages.ts` の共通の文 `CELL_NOTE` は「セルから bash を呼ぶ最短形は `sh(command)`」だけに縮め、行き先の指示は分類の行に任せる。
- 代替案: `CELL_NOTE` の「tsrepl のセルに書いてください」を残す。不採用とした。S2 の大半が読み取りなのに、tsrepl へ誘導してしまう。

### 8. 提供しないグローバルの一覧を REPL コアで 1 つにする
`repl/context.ts` に、意図的に提供しないグローバル(`process`、`Bun`、`require`)と、それぞれの代わりの手段を対応づけた一覧を置く。この一覧を使う箇所は 2 つある。
- `repl/format.ts` の `suggestFix`: 一覧に載った名前の `ReferenceError` のとき、その代わりの手段を返す。
- `tools.ts` の `TSREPL_DESCRIPTION`: 「セルに無いもの」の 1 行を、この一覧の名前から作る。

提案文は `await use("node:...")` を軸にし、`Bun` にだけ「`sh()` はルートのセッションのみ」と添える。どちらのセッションでも正しい文なので、`suggestFix` にセッションの情報を渡す配線は要らない。一覧と提案文は `repl/` の中で閉じ、guard や後段の機能を参照しない。
- 対価: 説明文(tsrepl の要件「ツール説明の use() の書き方」のシナリオ「無いグローバルの明示」)と提案文(要件「未提供のホストグローバルへの参照の提案」)が同じ名前の集合を使うことを、1 か所の定義で保証する。
- 代替案: `format.ts` と説明文に名前を直書きする。不採用とした。`ALLOWED_GLOBALS` を変えたとき、3 か所が食い違う。
- 撤回条件: 一覧を使う箇所が 1 つに減ったら、一覧をその箇所へ畳む。

### 9. code-mode プロンプトの例を置き換える
`sh("cat package.json")` の例は、`const fs = await use("node:fs/promises")` でファイルを読む例に置き換える。tsrepl の説明文の `use()` の行は、`node:` / `bun:` / 相対パスの例をすべて `await use(...)` の形にする。
- 代替案: `sh("cat ...")` の例を残し、注記で read の利用を勧める。不採用とした。コード例は注記より強く真似されるので、ファイルを sh で読む書き方を教え続けることになる。

### 10. Python の禁止の逃げ道は既存のモードだけにする
P3 にだけ効く別の設定は作らない。Python のプロジェクトでどうしても使う利用者は、`SPIRITS_ACTION_GUARD=warn` または `off` で起動する。README はこれを「推奨しない」という位置づけで書く。
- 代替案: P3 だけは `warn` / `off` でも止める。不採用とした。公開している製品で、Python のプロジェクトを開いた利用者に回避手段が無くなる。

## Risks / Trade-offs

- [Risk] シェルの `-c` の分類し直しで、これまで通っていた直接の呼び出しが S に該当するようになる(例: `bash -c 'cmd | awk ...'`)。→ Mitigation: タスク 3.3 で実セッションログを新旧の `classify` にかけ、新たに該当する件数と中身を確認する。誤検出はフィクスチャに加える。決定 5 の撤回条件に当たれば、S 系への適用を外す。
- [Risk] Python のプロジェクトでは、`pytest` などのプロジェクト自身の実行も止まる。→ Mitigation: README に「推奨しない」と明記し、`SPIRITS_ACTION_GUARD` での回避方法を書く。P3 のブロック理由にもモードの切り替えの文は残る。
- [Risk] P3 の名前の一覧に漏れがあり、まだ挙げていない Python のツールが通る。→ Mitigation: 一覧は `rules.ts` の 1 か所にあり、追加は 1 行とシナリオで済む。
- [Risk] promptGuidelines が長くなり、システムプロンプトの規則の節が膨らむ。→ Mitigation: 4 項目の合計を 534 文字(現行 356 文字の 1.5 倍)以内に収め、タスク 5.3 で文字数を確かめる。1.5 倍という値に測定上の根拠は無く、膨張を見える形にするための目安である。
- [Risk] sed の表示コマンドの構文解析が、正しい表示スクリプトを不一致と判定する。→ Mitigation: 不一致はブロックする方向に倒れるので、今と同じ挙動に留まる。測定で見た形(複数範囲、パターン範囲、1 行)はシナリオで固定する。
- [Risk] `managed-pi-compat` の期待値やテストが、旧来の規則の文面を一字一句持っている。→ Mitigation: タスク 6.2 で、文面を照合する箇所を洗い出して更新する。

## Migration Plan

データの移行はない。拡張バンドルを入れ替えると、次のセッションから新しい規則と判定が効く。戻すときは前の版のバンドルに戻す。判定だけを止めたいときは `SPIRITS_ACTION_GUARD=warn` または `off` を使う。
