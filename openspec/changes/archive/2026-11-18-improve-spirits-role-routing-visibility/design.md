# Design

## Context

動機は proposal に書く通りで、実測したセッションではステップの記録だけが書かれ、振り分けそのものは走っていなかった。表示面は現在 4 つあり、値の出所が揃っていない。

| 面 | 今の値の出所 | 振り分けが無効なとき |
|---|---|---|
| badge | ルーティングの role 報告 (リクエスト時) と、`/spirits-role`・セッション開始・分岐移動での位相からの解決 | ロックのロールを描く |
| 一覧の行の説明 | `resolveRequestPlan` と同じ解決 | 応答があると断言する |
| status | 同じ解決 + ルーティングが覚えた直近リクエスト | 1 行目だけが無効を述べる |
| 設定時の警告 | 書き込んだ値を fold した解決 | 手順を示すが実行不能なことがある |

badge だけが「リクエストの副次記録」として別系統になっており、リクエストが来ない限り、また設定の解決と無関係な値を出しうる。

セッションの開始では、ロックは分岐の `spirits_role` の記録から戻るが (`commands/register.ts` の `session_start`)、継続中のステップは再読み込みのときだけ戻り、それ以外の開始では `{ step: null }` を追記して終える (アーカイブ済みの design Decision 12)。開き直したセッションの badge と次のリクエストが、閉じる前と違うのはこのためである。

一次根拠の文書: managed 経路は phase 文書 (`docs/spirits-m*.md`) の対象外で、`docs/spirits-design.md` が managed 経路の詳細を委ねる `docs/spirits-managed-pi-design.md` を正とする (`openspec/config.yaml` の design rules との対応)。

ホスト (固定版 1.5.0) については、公式 artifact の型と実装で次を確認した:

- `ExtensionContext` は `model`、`scopedModels`、`thinkingLevel`、`mode` を読む。`scopedModels` の注釈は「`--models` / `enabledModels` を利用できるカタログに対して解決した集合。`/scoped-models` と同じ集合で、スコープ指定が無ければ空」となっている (`dist/core/extensions/types.d.ts`)。
- `model_select` は `source` として `set` / `cycle` / `restore` を持つが、`restore` の発火箇所は確認できなかった (`dist/core/agent-session.js`)。セッション開始時の復帰は `session_start` 側で受けられる。
- `thinking_level_select` は解決後のレベルが実際に変わったときだけ発火し、モデル切り替え時の丸めで変わっても発火する (`dist/core/agent-session.js`)。
- footer は拡張 status を key の昇順で 1 行に並べ、端末幅で末尾を省略する。統計行に出るモデル名は選択中のモデルの ID で、`session.routedModel` は拡張面に出ない (`dist/modes/interactive/components/footer.js`)。
- model selector は `scopedModels` が非空なら `scoped` で開き、`tui.input.tab` で `all` と切り替える。`/model <語>` はスコープ指定下にある集合しか引かない (`dist/modes/interactive/components/model-selector.js`、`dist/modes/interactive/interactive-mode.js`)。
- `/scoped-models` は有効モデルの付け外しを編集し、保存すると `enabledModels` に書く (`dist/core/slash-commands.js`、`dist/modes/interactive/interactive-mode.js`)。
- `input` のハンドラは登録順に 1 つずつ `await` され、`{ action: "handled" }` を返したハンドラで入力の処理が止まる (`dist/core/extensions/runner.js` の `emitInput`)。async のハンドラで待つ間、入力はエージェントに渡らない。
- `ctx.ui.select(title, options, { timeout, signal })` はカウントダウンを表示して自動で閉じ、時間切れでは `undefined` を返す (`ExtensionUIDialogOptions`、`dist/modes/interactive/interactive-mode.js`)。時間切れは Esc と同じ cancel の経路で閉じるので、戻り値だけでは両者を区別できない (`dist/modes/interactive/components/extension-selector.js`)。カウントダウンは生成時から 1 秒刻みの `setInterval` で数え、待ち時間より前には閉じない (`dist/modes/interactive/components/countdown-timer.js`)。`signal` の abort でも `undefined` で閉じる。`ctx.ui.confirm` は同じ selector の上に `Yes` / `No` の固定の選択肢で作られており、選択肢の名前を変えられない。
- `input` イベントは送り元を `source` (`interactive` / `rpc` / `extension`) で持つ (`dist/core/extensions/types.d.ts`)。
- `hasUI` は RPC でも真になるので、対話端末かどうかは `ctx.mode === "tui"` で判定する (現行の一覧も同じ判定で開く)。

## Goals / Non-Goals

**Goals:**

- badge を 1 本の書き込み口を持つ状態の射影にし、ルーティングと同じ解決をリクエスト前に示す。
- 振り分けの有無を、常時表示面・一覧・status・警告・ステップ開始時の確認のすべてで同じ言い方をさせる。
- 警告と status が示す手順を、そのセッションで実際に実行できるものにする。
- 開き直したセッションのロック・継続中のステップ・badge を、閉じる前と同じにする。

**Non-Goals:**

- 振り分けの規則 (ロールの解決順、ステップの開始と解除、thinking レベルの解決) は変えない。変えるのはセッションの開始でステップを終えるかどうかだけである。
- 物理モデルが選択されているセッションで割り込んで振り分けることはしない。
- `spirits/auto` を設定やスコープへ自動的に書き込むことも、セッションのモデルを代わりに選ぶこともしない。
- 一覧に新しい行 (専用の状態行) を追加しない。既存の行の説明の中で状態を述べる。
- 対話端末でないセッション (RPC / print) で、手順の案内やステップ開始時の確認を出さない。

## Decisions

### 1. badge は履歴ではなく射影とし、導出と描画は commands 層に置く

- 採用: badge の値を、その時点の設定・ロック・継続中のステップ・セッションのモデルから `resolveRequestPlan` で導出する。導出と描画は `commands/role.ts` (語彙と整形) と `commands/register.ts` (呼び出し) に置き、ルーティングの role 報告は badge に書き込まない。`index.ts` の `onRole` 配線を外し、`onRequest` (status の直近リクエスト) だけを残す。
- 代替案: 現行どおりルーティングの報告を badge の供給元にし、無効時の分岐だけ足す。却下理由: リクエストが来ない限り古い値が残る、拡張の再読み込みで消える、一覧と status が既に持っている解決を 4 番目の系統として重ねることになる。
- 代替案: 導出を routing 層 (`routing/plan.ts`) か新しい共有モジュールに置く。却下理由: routing 層に表示の語彙が入るか、新しい共有境界 (`registry:layer-members` の編集) が要る。commands 層は routing とホストの両方への依存が既に許可されており (`registry:layers`)、`commands/register.ts` は既に routing を読んでいるので、継ぎ目は増えない。
- 帰結: 一覧・status・badge・ルーティングが同じ 1 関数の結果を共有する。
- 撤回条件: commands 以外の層 (例えば routing) が badge の値を必要とするようになったら、導出を shared 層へ移す。

### 2. 描き直しはイベント駆動、購読は commands 層

- 採用: `commands/register.ts` が `input`、`model_select`、`thinking_level_select`、`session_start`、`session_tree` を購読し、`/spirits-role` の変更後とあわせて描き直す。`input` はステップ機構の入力処理 (`routing/register.ts`) より後のハンドラで受け取る。`index.ts` で routing を先に登録するので後になり、この順序はテストで固定する。
- 代替案: `routing/register.ts` が購読し、`RoutingHooks` に 1 項目足して `index.ts` 経由で描く。却下理由: 既存の hooks の拡張点を太くし、描画の経路が 2 本になる。
- 代替案: 一覧とコマンドからの変更だけを描き直す。却下理由: `/model` と `/thinking` はホストのコマンドで、spirits は設定を書いていないため変更を検知できず、badge が実態から離れる。
- 代替案: 定期描画。却下理由: ホストに拡張が周期的に走る面を持たせられないし、走る必然が無い。
- 対価: 購読が 2 つ増える代わりに、`/model` と `/thinking` の後に badge が古い値を出し続ける誤り (シナリオ `モデル切り替えで badge が従う`、`thinking レベルの切り替えで badge が従う`) が無くなる。
- ステップの run が落ち着いたとき (`agent_settled`) も描き直す。非継続ステップが settle で終わると位相はロックへ戻るので、描かないと badge だけが strong のまま残り、次のリクエストの解決と一致しなくなる (検証で再現した、settle 後に badge だけ strong が残る経路)。
- 代替案: 描き直す時点を有限のイベントに限り、settle 後は badge を古いままにする。却下理由: 状態の射影を名乗る以上、位相が変わった時点を漏らすと「次のリクエストの解決」と食い違う。
- 撤回条件: ホストが footer に振り分け後の物理モデルとロールを出す拡張面を提供し、badge 自体が不要になったら、購読ごと外す。

### 3. 無効時の badge は `[off]` だけ、応答モデルは出さない

- 採用: 有効時は `[<role> <level>]` (レベルが解決できなければ role のみ) と別の status key の物理モデル、無効時は `[off]` のみで第 2 key は消す。normal が解決できない `[!]` のときも、応答するモデルが無いので第 2 key は消す。
- 代替案: 無効時は無表示。却下理由: 「spirits が動いていない」「表示が壊れた」と区別できない。
- 代替案: 無効時も解決値を添える (`[off normal medium]`)。却下理由: ホストの統計行が選択中の物理モデルとレベルを既に出しており、二重表示になる。

### 4. 物理モデルの表示は provider を落として 24 文字で省略する

- 採用: 第 2 key は provider を除いたモデル ID とし、24 文字を超えたら先頭 23 文字に `…` を付けて 24 文字にする。桁数は `src/constants.ts` の定数とする。key 名はロールの key の前綴になるようにし、footer の key 昇順でロールが先に並ぶことをテストで固定する。一覧と status は幅に余裕があるので `provider/id` のまま出す。
- 代替案: `provider/id` をそのまま出す。却下理由: 長い参照 (数十桁) がそのまま出て、行全体を共有する他の拡張の表示と自分のモデル表示の両方を footer の省略が削る。
- 代替案: footer の省略に任せる。却下理由: 省略は行の末尾に掛かるので、後に置いたモデル表示から失われる。
- 代替案: 先頭と末尾を残す。却下理由: 整形規則が増える。24 文字は実運用で応答モデルになる ID (`ernie-5.5-flash-preview` 21 文字など) をほぼ収める。
- 撤回条件: 24 文字で判別できない ID が実運用で出たら、桁数の定数を見直す。
- 2 つの key は独立に書く。片方の書き込みが例外を投げても、もう片方の書き込みと応答は止めない (既存の降格の扱いと同じ)。

### 5. 振り分けの有効・無効はセッションのモデルで判定し、判定は shared 層の 1 関数に置く

- 採用: 振り分け用モデルの provider と ID との比較を `src/constants.ts` の 1 関数に置き、一覧・status・badge・警告・ステップ開始時の確認で同じ判定を使う。`commands/register.ts` の `isPhysicalSelection` はこの関数に置き換える。`routing/child.ts` は先に api で仮想モデルかどうかを判定してから比較するので、比較の部分だけをこの関数に置き換え、api の判定は残す。
- 代替案: ホストが保持するルーティング後の物理モデルを参照する。却下理由: その値は拡張面に露出していない (上の確認)。
- 代替案: 判定の重複 (commands と routing の 2 か所) を許容する。却下理由: 比較は短く ARCH-DUP の検査には上がらないが、判定規則が変わるときに直す箇所が 2 つ残る。routing は shared に依存できるので、新しい層境界は要らない。
- 対価: shared に公開関数が 1 つ増える代わりに、`src/commands/register.ts` の `isPhysicalSelection` と `src/routing/child.ts` の比較の 2 か所が 1 か所になる。
- 撤回条件: commands と routing で「振り分け用モデル」の判定が分かれる必要が出たら (例えば routing が別の仮想モデルも振り分けるようになったら)、関数を各層に戻す。

### 6. スコープの診断はセッションのスコープ集合を読み、手順文は commands の 1 関数で作る

- 採用: 案内を作る際は `ExtensionContext.scopedModels` を読み、非空かつ振り分け用モデルを含まない場合はその事実を出す。対話端末 (`ctx.mode === "tui"`) では、selector の範囲切り替えと `/scoped-models` を名指す手順を添える。スコープが空なら、対話端末では簡潔な手順 (振り分け用モデルを選ぶ) だけを出す。対話端末でなければ手順は出さない。
- 手順文の生成は `commands/role.ts` の 1 関数にし、設定時の警告・status・ステップ開始時の確認の 3 か所から呼ぶ。振り分け用モデルの綴りは provider と ID の定数から組み立てる。
- 代替案: 設定の `enabledModels` だけを読む。却下理由: `--models` での起動時スコープを取りこぼし、また設定に無いのにスコープが効いているセッションで嘘の手順を出す。
- 代替案: 3 か所で手順文を別々に作る。却下理由: 今回の不具合の一因が、警告文だけが実行不能な綴りを出していたことであり、同じずれを 3 か所に作ることになる。
- 代替案: 対話端末でなくても設定ファイル (`enabledModels`) や起動オプション (`--models`) を名指す。却下理由: 利用者の判断で対話端末に限定した。対話端末でないセッションの利用者は、事実 (スコープ外) だけで足りる。
- 注意: 選択器の内部状態 (現在 `scoped` で開いているか) は読めない。出すのは「どちらの操作でも到達できる」という事実どまりにし、画面上の位置を指示しない。
- ロールの対象の候補は、その時点で利用できる物理モデル (振り分け用のモデルを除く) とし、セッションのモデルスコープで制限しない。
- 代替案: 一覧の候補をセッションのスコープと交差させる。却下理由: ルーティングもコマンド行も対象をスコープで制限しておらず、一覧だけが別規則になる。スコープが `spirits/auto` だけのセッションでは候補が空になり、対象を戻す `unset` も選べなくなる。
- 代替案: 保存済みの対象がスコープ外であることを行の説明に出す。却下理由: 対象はスコープと独立に解決されるため診断が誤りやすく、一覧にスコープの診断を出さないという要件とも重なる。

### 7. ステップ開始時は、期待と実態が食い違うたびに 10 秒の確認を出す

- 採用: 対話端末で、利用者が端末から送った入力 (`source` が `interactive`) がステップを開始し、振り分けが無効で、そのステップに期待されるロール (明示のロールまたは thinking の設定、またはステップの既定ロール) があるとき、毎回 `ctx.ui.select` で「続行」「中止」の 2 択を 10 秒の timeout で出す。続行を先頭に置き、反射的な Enter が時間切れと同じ結果になるようにする。本文には、そのステップに期待するロールが今は使われないことと Decision 6 の手順を書く。時間切れと続行では入力をそのまま進め、中止と Esc では `{ action: "handled" }` を返して入力を送らず、ステップを入力前の状態に戻す。待ち時間は `src/constants.ts` の定数とする。
- 時間切れと Esc の区別: `select` に待ち時間の `timeout` (カウントダウンの表示用) と `signal` を渡し、待ち時間より 100 ミリ秒早く発火する自前のタイマーで `signal` を abort する。ホストのカウントダウンは待ち時間より前に閉じないので、時間切れは必ず自前のタイマーが先に閉じる。自前のタイマーが発火した後の `undefined` を時間切れ、それより前の `undefined` を Esc とする。早める幅は `src/constants.ts` の定数とする。
- ダイアログが例外を投げたとき (ホストが拒んだとき) は、待たずに入力を進める。既存の降格の扱い (ホストが拒んだ面だけを失う) と同じである。
- 拡張機能が送った入力 (`source` が `extension`) と RPC の入力では確認しない。確認の目的は、利用者自身が誤解したまま進むのを防ぐことであり、利用者が送っていない入力で利用者を待たせない。
- 配置: 確認は `commands/register.ts` の `input` ハンドラに置く。routing の入力処理より後に走るので、開始したステップを位相から読める。
- 中止で戻す操作: routing の位相が、直前の入力で変えたステップを入力前の状態へ戻す操作を 1 つ公開する。入力の処理の前に位相が自分で控えた状態へ戻し、戻した結果をステップの記録として追記する (再読み込みと分岐移動が読む記録を合わせるため)。commands から routing への呼び出しは既に許可された向きである。
- 中止で戻す対象は、確認を出した入力が控えた状態に限る。入力ごとの rollback token と位相・分岐の世代を持ち、確認の入力と一致しないとき、および待ちの間に別の入力・位相の変更・分岐の移動があったときは戻さない。
- 代替案: 位相が持つ「直前の入力」のスナップショットを無条件に戻す。却下理由: 待ちの間に拡張入力が別のステップを開始したり、分岐を移動したりすると、その変化を上書きし、中止した入力の状態や移動先の記録を復元してしまう (検証で再現した、中止が別入力・移動先の状態を上書きする経路)。
- 代替案: `ctx.ui.confirm` を使う。却下理由: 選択肢が `Yes` / `No` に固定され、「中止しますか」という問いの向きを読み違えると逆の操作になる。
- 代替案: 1 セッション 1 回の通知だけにする。却下理由: 利用者の判断で、止まって直せる機会を毎回出すことにした。
- 代替案: 確認に「`spirits/auto` に切り替えて続行」を加える。却下理由: Decision 8 (セッションのモデル選択はホストに任せる) を裏返す。
- 代替案: ルーティング時に通知する。却下理由: 振り分けが無効なセッションではルーティング自体が呼ばれない。
- 代替案: 中止でもステップを開始したまま残す。却下理由: 入力は送られていないのにステップだけが継続中になり、次の idle 入力が期待しないロールで走る。
- 代替案: 中止では開始したステップを既存の `endStep()` で閉じるだけにする (継ぎ目を増やさない)。却下理由: 利用者の判断で、入力前の状態に戻すことにした。閉じるだけでは、前に継続中だったステップ (例えば `opsx-propose`) も終わり、利用者はそのコマンドを送り直す必要があり、それまでの idle 入力はロックのロールで走る。
- 代替案: Esc を時間切れと同じ「続行」にする (ホストの戻り値のまま)。却下理由: 利用者の判断で、閉じる操作は中止とした。
- 対価: 位相の公開操作が 1 つ増える代わりに、中止が状態を何も変えない (シナリオ `中止すれば入力前に戻る`)。
- 撤回条件: ステップ開始時の確認を廃止したら、この位相の操作も外す。

### 8. ホストのモデル選択を代行するコマンドは追加しない

- 採用: `spirits/auto` への切り替えはホストの `/model` と `/scoped-models` に任せ、spirits は手順を名指す。
- 代替案: 振り分けを有効にする専用コマンドを 1 つ増やし、ホストの API でセッションのモデルを選ぶ。却下理由: 「モデル選択と既定保存はホストに任せる」という既存の設計判断と、README に書かれた表面の違いの文書化 (専用コマンドが設定するのはロールの対象でありセッションのモデル選択ではない) を裏返す。到達性は手順を名指すことで足りる。

### 9. 固定値は constants に寄せる

- 採用: badge の語彙 (`off` と応答が無いことを示す語)、ロール表示とモデル表示の status key、モデル表示の桁上限、ステップ開始時の確認の待ち時間と時間切れを判定する自前のタイマーを早める幅、振り分け用モデルかどうかの判定は `src/constants.ts` に集約する。振り分け用モデルの綴りは provider と ID の定数から組み立て、警告文にハードコードしない。確認の待ち時間と幅も定数だが、`ManagedCommandsDeps` にテスト専用の差し替え口を 1 つ置く。
- 代替案: テストが実時間 10 秒を待つ。却下理由: 時間切れと Esc の境界は 100 ミリ秒差で、実時間では検査できない。差し替え口は本番の既定値を持たず、呼び出し側が渡したときだけ変わる。
- 代替案: 既存どおり警告文の中に綴りを書く。却下理由: 表示語彙が増えたときに 1 か所で変わらなかったことが今回の不具合の一因 (警告文が実行不能な綴りを出していた) なので、綴りの出所を 1 か所に寄せる。

### 10. セッションの開始では、分岐の記録からロックと継続中のステップを戻す

- 採用: 種類を問わずセッションの開始 (起動時の再開、`/resume` による復帰、分岐作成、再読み込み) で、分岐の最新の `spirits_step` の記録が一覧に載るステップを示すなら、そのステップを継続中として戻す。ただし再読み込み以外の開始では、継続しないステップ (`continuing: false`) の開いた記録は戻さない。その記録は run の途中で閉じたことを示しており、中断された run はロックへ戻るという既存の規則 (`strong フェーズからの復帰` / `中断後も戻る`) に従う。再読み込みは run の途中でも起こりうるので、現行どおり継続しないステップも引き継ぐ。ロックは現行どおり `spirits_role` の記録から戻す。新規セッションは記録を持たないので何も戻らない。開始時に `{ step: null }` を追記する処理は撤去する。badge はこの戻した状態から射影で描く。
- 再読み込み以外の開始で、記録が開いたままの継続しないステップを棄却したときは、その棄却をステップの記録として追記する。継続中のステップを戻す開始では追記しない。
- 代替案: 棄却を何も追記せずメモリ上だけで外す。却下理由: runtime は再読み込みで置き換わるため、棄却した事実が失われ、次の再読み込みが同じ古い記録を戻す (検証で、復帰直後は normal、その後の再読み込みで strong が復活することを確認した)。
- これはアーカイブ済みの design Decision 12 のうち「再読み込み以外の開始ではステップを終える」を撤回する。Decision 12 の目的 (ステップの記録と実際の位相を一致させる) は保たれる。開いた時点で戻すか棄却するかを決め、棄却したときはその記録を追記するので、後の再読み込みが古い記録から想定外のステップを復元しない。
- 戻した継続中のステップは、再読み込みのときと同じく、ロールと thinking レベルを次のリクエストで現在の設定から解決する。
- 代替案: ロックだけを戻し、ステップは現行どおり終える。却下理由: 利用者の判断で、閉じる前の状態をすべて戻すことにした。strong のステップの途中で閉じたセッションを開くと、続きが strong で走らず badge もそれを示すので、今回の不具合と同じ種類の誤解が残る。
- 代替案: 復帰だけで戻し、分岐作成では終える。却下理由: 分岐の移動は既に記録に合わせて継続中にしており (`session_tree`)、分岐作成だけを例外にすると同じ分岐の記録の読み方が 2 通りになる。
- 撤回条件: 古いセッションを開いたときにステップが残ることが実運用で妨げになったら、開始の種類ごとに戻す範囲を分ける。

## Risks / Trade-offs

- [Risk] `thinking_level_select` はレベルが実際に変わったときだけ発火するので、イベント漏れのように見えるケースがある → Mitigation: 同じ状態変化を起こす `model_select` と `input` でも描き直すため、表示は直後に収束する。テストで「レベルが変わらない操作では描き直しが起きなくても表示は正しい」ことを確認する。
- [Risk] `restore` を名乗る `model_select` の発火箇所が確認できない → Mitigation: 復帰は `session_start` の描き直しでカバーする (現行も同じ)。発火が確認できない間は、復帰経路の badge は `session_start` を正とする。
- [Risk] 毎入力で直近の成功レスポンスを辿るコスト → Mitigation: 辿るのは最初の成功する assistant メッセージまでで打ち切る現行の実装を使い、run の最中には描かない (入力は 1 run に 1 回)。入力のたびに 1 件の走査で、ループにはしない。
- [Risk] badge が「次になされる解決」になるので、一覧を開いている間に設定を変えたときの値と run 中の実測がずれる瞬間がある → Mitigation: 一覧も status も同じ解決を開いた時点で読み直す。run の途中の変更は既存の仕様どおり次のリクエストから効き、badge も次の入力で従う。
- [Risk] badge の綴りを変えるので、文字列を期待する既存テストと文書が壊れる → Mitigation: 対象は `managed-commands.test.ts`、`managed-role-panel.test.ts`、`routing-integration.test.ts`、`routing-phase-reload.test.ts` の badge の期待値と、4 か国の README、`docs/spirits-managed-pi-design.md`。tasks で洗って同時に更新する。
- [Risk] 手で編集した設定は拡張の再読み込みまで badge に効かない → Mitigation: 境界として仕様シナリオに書き、文書にも同じことを記す。設定ファイルの監視はしない。
- [Risk] ステップ開始時の確認は、物理モデルを意図して使う利用者にも毎回 10 秒の待ちを課す → Mitigation: 期待されるロールがあるステップに限り、続行を選べば即座に進む。対話端末でなければ出さない。
- [Risk] 確認の待ちの間に別の入力やセッションの切り替えが起きる → Mitigation: 確認できているのは、1 つの入力の中でハンドラが順に `await` されることだけで、入力ごとの直列化と待ちの間のセッション切り替えは未観測 (Open Questions)。待ちの後に rollback token と位相・分岐の世代を照合してから戻し、tmux の実測 (tasks 10.4) で観察する。
- [Risk] 時間切れの直前 (100 ミリ秒以内) の Esc は時間切れとして扱われ、続行になる → Mitigation: 幅は定数で、人の操作では実質起きない。境界はテストで固定する。
- [Risk] 開き直したセッションで、古い継続中のステップが戻る → Mitigation: badge が戻ったステップのロールを示し、`/spirits-clear` かロックで終えられる。status も現在のステップを示す。
- [Trade-off] 一覧の説明文を仮定法にすると、既存の「実際に応答するモデルを出す」という文言との関係が二段階になる → Mitigation: `一覧の説明の thinking レベルは要求に載るレベルを示す` も MODIFIED に含め、一致が仮定に対するものだと本文に書く。

## Open Questions

- 振り分けを既定で使いたい利用者向けに、`spirits/auto` を既定モデルへ保存する導線を別の変更で用意するか。**用意する方向で `add-spirits-role-save-row` を提案済み** (`/spirits-role` 一覧の最上位の `save` の行と `/spirits-role save`)。既知の落とし穴への答えは実測で決めた: `defaultProvider: "spirits"` / `defaultModel: "auto"` の新しいセッションは normal が解決できなければ badge `[!]` で最初のリクエストが `spirits/auto has no normal model: ...` になる (公式 Pi 1.5.0 で再現)。よって save は normal の対象が解決できるときのみ既定モデルのキーを書く。本変更では扱わない。
- ステップ開始時の確認を待っている間に、利用者が別の入力を送ったり、セッションを切り替えたりしたときのホストの扱い → **tasks 10.4 で実測済み (公式 Pi 1.5.0 の対話 TUI)**。`ctx.ui.select` の確認はモーダルで、開いている間の打鍵は選択ウィジェットが受け取り、通常の入力欄には入らない。したがって対話 TUI からは待ちを追い越す入力が送れず、`/tree` などのセッション操作も開始できない (Enter は強調表示中の先頭候補 `continue` を確定する。既定が continue なので誤った Enter は入力を送る)。時間切れ (10 秒、表示は 1 秒刻み) では入力が送られ、Esc では送られず badge も変わらなかった。待ち中の上書きは Occur なので、Decision 7 の rollback token と位相・分岐の世代の照合は、拡張から直接入力が届く経路 (テストで固定) に対してそのまま残す。
