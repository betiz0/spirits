# Spec Delta

## ADDED Requirements

### Requirement: 振り分け先の収容量に会話を収めるための先行圧縮
システムは、振り分け用のモデルを選択しているセッションで、次のリクエストで応答する物理モデルの収容量と、入力を受信した時点で積まれている会話(展開前の本文と、ブランチ射影の和の推算)とを、リクエストを開始する前に比べなければならない。(SHALL) 測った量が pi の自動 compaction の判定に使う閾値(収容量から reserve を引いた値)を越えている場合、システムはそのリクエストの前に会話の圧縮を行い、圧縮の直後に同じ基準でもう一度測らなければならない。(SHALL) 比較する収容量はロールではなく実際に応答する物理モデルの収容量とし、閾値・reserve・keep は pi が設定から解決するものと同じ値を用い、spirits 側に新しい数値の既定を増やしてはならない。(SHALL) スキルとテンプレートの展開で増える量と、実行中の run 中のロール切り替えは判定の保証範囲外とし、host の送信前圧縮と overflow 復旧に任せる。

#### Scenario: 大きい枠のロールから小さい枠の既定へ戻る最初の入力
- **GIVEN** 振り分け用のモデルが選択され、strong の対象は収容量 128000、既定の normal の対象は収容量 32000 で、strong のステップは終わっている
- **AND** 会話の推算が normal の対象の閾値(収容量から reserve を引いた値)を越えている
- **WHEN** 続けて対話端末で idle な入力でリクエストする
- **THEN** 会話リクエストより前に要約のためのモデル呼び出しがあり、会話は圧縮されたうえで normal の対象へ送られる

#### Scenario: 収まっている場合は圧縮しない
- **GIVEN** 振り分け用のモデルが選択され、会話は応答する normal の対象の閾値に収まっている
- **WHEN** idle な入力でリクエストする
- **THEN** 要約のためのモデル呼び出しは 0 件で、リクエストはそのまま normal の対象へ送られる

#### Scenario: 圧縮はロールと thinking を変えない
- **GIVEN** 先行する圧縮が成立した直後のリクエストである
- **WHEN** そのリクエストが走る
- **THEN** 応答するロールと要求される thinking レベルは圧縮前と同じ解決である

### Requirement: 圧縮後も収まらないリクエストは送らない
システムは、圧縮の直後に測っても会話が応答する物理モデルの閾値に収まらない場合、その会話リクエストを送ってはならない。(MUST) 圧縮が行えなかった場合、つまり圧縮できる会話が無くもともと閾値を超えている場合と、圧縮の要約が失敗した場合も、同じく会話リクエストを送ってはならない。(MUST) 拒否の判定に使う閾値は、自動 compaction が有効なときの pi の閾値と同一の数値とし、`enabled` の値に依存しない。(SHALL)

#### Scenario: 圧縮後も枠を超える
- **GIVEN** 振り分け用のモデルが選択され、normal の対象の収容量は 32000 で、圧縮後に残る直近の会話だけが閾値を大きく越えていて、要約では減らせる部分が残っていない
- **WHEN** idle な入力でリクエストしようとする
- **THEN** normal の対象への会話リクエストは 0 件で、run は始まらない

#### Scenario: 公称の収容量の内側でも reserve を越えていれば断る
- **GIVEN** normal の対象の収容量は 32000、reserve は 16384 で、圧縮後に残る会話の推算は 20000(32000 には収まるが閾値 15616 を越える)であり、これ以上減らせる部分が無い
- **WHEN** idle な入力でリクエストしようとする
- **THEN** 会話リクエストは 0 件で、理由は推算が収容量ではなく閾値に収まらないことを示す

#### Scenario: 圧縮できる会話が無く、もともと枠を超えている
- **GIVEN** 振り分け用のモデルが選択され、normal の対象の閾値を会話が越えていて、会話の最後の記録が compaction である
- **AND** pi の compaction はその会話に対して新しい compaction を作らない(host の文言は観測であり、契約の照合条件にしない)
- **WHEN** idle な入力でリクエストしようとする
- **THEN** 会話リクエストは 0 件で、run は始まらない

#### Scenario: 圧縮の成立後は送る
- **GIVEN** 会話が normal の対象の閾値を越えていたが、先行する圧縮の直後に測ると収まる
- **WHEN** その入力のリクエストが続く
- **THEN** 会話リクエストは normal の対象へ 1 件送られる

### Requirement: 送らないことを選んだ理由を出す
システムは、リクエストを送らないことを選んだとき、その判断ごとに理由を 1 件通知しなければならない。(SHALL) 理由は、応答するはずだったモデル、その収容量、reserve を含んだ閾値、測った会話の量、および送らないことを選んだ根拠を名指さなければならない。(SHALL) 通知は対話端末と RPC のセッションに届かなければならない。(SHALL) 1 つの判断に対して理由を複数回出してはならない。(MUST NOT)

#### Scenario: 圧縮後も収容量を超えていたことを名指す
- **GIVEN** 先行する圧縮の直後に測っても normal の対象の閾値を超えている
- **WHEN** リクエストを送らない判断をする
- **THEN** 通知は normal の対象のモデルと収容量と測った会話の量を出し、圧縮後も収容量を超えていたことを示す

#### Scenario: 圧縮が成立しなかったことを名指す
- **GIVEN** 圧縮の要約が provider のエラーで失敗した
- **WHEN** リクエストを送らない判断をする
- **THEN** 通知は圧縮が成立しなかったことを名指し、失敗の理由を添える

#### Scenario: RPC の拒否は拡張通知として届く
- **GIVEN** RPC セッションで、normal の対象の閾値に会話が収まらない状態である
- **WHEN** 入力を送ってリクエストを送らない判断になる
- **THEN** 拒否の理由は pi の拡張通知(method `notify`)としてセッションに届き、会話リクエストは 0 件で、run は始まらない

### Requirement: 送らないことを選んだときに入力とロールの状態を残す
システムは、リクエストを送らないことを選んだとき、ロック中のロール、継続中のステップ、および role の表示を、その入力を受信する前の状態へ、既存のステップ開始確認と同じ巻き戻しを使って戻さなければならない。(SHALL) 戻った状態は、リロード、再開、およびブランチ移動のあとに読み返されて同じ位置でなければならない。(SHALL) 対話端末では入力された本文を入力欄へ戻し、RPC では編集欄の復元リクエストを最善を尽くして出さなければならない。(SHALL) 本文の復元が保証されない経路では、本文が戻らない可能性があることを理由に含めなければならない。(SHALL) 送られなかった run のステップが継続中のまま残ってはならない。(MUST NOT)

#### Scenario: 対話端末で断って本文を残す
- **GIVEN** 対話端末で、normal の対象の閾値に会話が収まらない状態である
- **WHEN** 本文を入力して送信し、リクエストを送らない判断になる
- **THEN** 本文は入力欄に戻り、role のロックと継続中のステップと role 表示は入力前と同じで、run は始まっていない

#### Scenario: 断ったあとに読み直すと入力前の位置である
- **GIVEN** リクエストを送らない判断が入力に対して行われた
- **WHEN** そのセッション記録からロールとステップを復元する
- **THEN** ロック中のロールと継続中のステップは、その入力を受信する前と同じ位置である

#### Scenario: 収容量のあるモデルへ替えてから同じ本文を送る
- **GIVEN** 上記の判断で本文が入力欄に戻っている
- **AND** 利用者が振り分け先の normal を収容量の大きいモデルへ替えるか、収容量の十分な物理モデルを選ぶ
- **WHEN** 戻った本文を送る
- **THEN** そのリクエストは走る

#### Scenario: 継続するステップの開始コマンドを断る
- **GIVEN** 継続するステップの開始コマンドを打つと、振り分け先の閾値に会話が収まらない
- **WHEN** そのコマンドを送信してリクエストを送らない判断になる
- **THEN** そのステップは走っておらず、ロールの表示は入力前のままである

#### Scenario: 本文を戻せない経路ではその旨を出す
- **GIVEN** 編集欄の復元が効かない経路から入力され、リクエストを送らない判断になった
- **WHEN** 理由を通知する
- **THEN** 理由は、本文が戻らない可能性があることと実行しなかったこととを含み、run は始まらない

### Requirement: 判定を適用する入力と適用しない入力
システムは、対話端末と RPC のモードで、モデルリクエストを開始する入力に限り、収容量の判定、先行する圧縮、および送信を拒否する判断を適用しなければならない。(SHALL) 実行中の run に合流する入力、モデルリクエストを開始しない入力、拡張から送られた入力、および print と JSON のモードの入力では、圧縮も行わず、送信を拒否もしない。(MUST NOT) 判定のために実行中の run を中断してはならない。(MUST NOT) 判定は展開前の本文と受信時点の会話に基づき、スキルとテンプレートの展開で増える量は host の送信前圧縮に任せる。先行圧縮の在職中に届いた入力は、この要求の通常の判定ではなく、在職中の拒否の要求で扱う。

#### Scenario: 応答中の steering 入力では判定しない
- **GIVEN** run が実行中で、その run が応答するモデルの収容量に会話がかさみそうである
- **WHEN** 実行中に入力を steering として送る
- **THEN** 要約のためのモデル呼び出しは 0 件で拒否も無く、実行中の run はそのまま進む

#### Scenario: モデルを実行しない入力では判定しない
- **GIVEN** 会話は振り分け先の閾値を超えている
- **WHEN** 拡張が登録したコマンドを入力する
- **THEN** 圧縮も拒否も無く、そのコマンドは実行される

#### Scenario: 拡張から送られた入力は対象にしない
- **WHEN** 拡張から送られた入力によってリクエストが始まる
- **THEN** 収容量の判定による拒否は行われず、リクエストは解決された対象へ送られる

#### Scenario: print と JSON のモードは素通りする
- **GIVEN** 会話は振り分け先の閾値を超えていて、pi は print または JSON モードで走っている
- **WHEN** そのモードに入力が渡される
- **THEN** gate による圧縮も拒否も無く、リクエストは pi の通常の挙動で送られる

#### Scenario: スキル起動のコマンドでは展開前の本文で判定する
- **GIVEN** 会話は振り分け先の閾値を超えている
- **WHEN** スキルを起動するコマンドを入力する
- **THEN** 判定は行われ、その判定はスキル展開前の本文と受信時点の会話に基づく

### Requirement: 先行圧縮の要約先の解決
システムは、gate が走らせる先行圧縮に伴う要約のリクエストについて、要約対象の推算がロールの対象の閾値に収まらない場合、現在のカタログと資格情報で解決でき、かつその推算を収容量に収める直近の成功レスポンスの物理モデルで解決しなければならない。(SHALL) gate の先行圧縮に属しないと判別される場合、または上記のモデルが解決できない場合は、ロールの対象で応じなければならない。(SHALL) gate に属さない要約のリクエスト(分岐の要約など)と、会話リクエストの解決先は、この規則で変えてはならない。(MUST NOT) gate の先行圧縮の要約の解決によって、ロールの位相、継続中のステップ、および直近のリクエストの報告を変えてはならない。(MUST NOT)

#### Scenario: 振り分け先より大きい会話の要約
- **GIVEN** 会話の量は 110000 で、normal の対象の収容量は 32000、直近の成功レスポンスは収容量 128000 のモデルによる
- **WHEN** gate の先行圧縮の要約のリクエストが走る
- **THEN** 要約は収容量 128000 のモデルで走り、圧縮後の会話リクエストは normal の対象で走る

#### Scenario: 収容できるモデルが無い
- **GIVEN** 直近の成功レスポンスのモデルも normal の対象と同じ収容量 32000 で、会話はそれを越えていて、他に利用可能な収容量の大きいモデルが無い
- **WHEN** gate の先行圧縮の要約のリクエストが走る
- **THEN** 要約はロールの対象で試みられ、失敗したときは送らない理由にそれが名指される

#### Scenario: 判別できないリクエストは従来どおり
- **GIVEN** gate の先行圧縮が走っていない
- **WHEN** 分岐の要約のリクエストが走る
- **THEN** 解決先はこれまでどおりロールの対象で、gate の規則は働かない

#### Scenario: 要約の解決は位相と報告を変えない
- **GIVEN** 継続するステップが走っており、そのステップのロールが strong に設定されている
- **WHEN** gate の先行圧縮の要約のリクエストが走る
- **THEN** ロックと継続中のステップは圧縮前と同じままであり、直近のリクエストの報告も圧縮前のものが残る

### Requirement: 自動 compaction の設定を打ち消さない
pi の自動 compaction が無効に設定されているとき、システムはその設定を打ち消して圧縮を行ってはならない。(MUST NOT) この設定下で会話が応答する物理モデルの閾値に収まらない場合、システムはその会話リクエストを送ってはならない。(MUST) 拒否に使う閾値は有効なときと同一の数値とする。

#### Scenario: 無効で枠を超えている
- **GIVEN** 自動 compaction が無効で、会話は normal の対象の閾値を超えている
- **WHEN** idle な入力でリクエストしようとする
- **THEN** 要約のためのモデル呼び出しは 0 件で会話リクエストも 0 件であり、理由は自動 compaction が無効であることを名指す

#### Scenario: 無効でも収まっている
- **GIVEN** 自動 compaction が無効で、会話は normal の対象の閾値に収まっている
- **WHEN** idle な入力でリクエストする
- **THEN** リクエストは normal の対象へ送られる

### Requirement: 先行圧縮の在職による入力の拒否
システムは、先行圧縮の経路の最初の await より前に同期で在職を記録し、gate ハンドラの全出口(続行、拒否、および例外)でこれを下ろすまで、`input` イベントに届いたすべての入力を、通常の収容量の判定を通さず、送らずに `handled` と 1 件の理由通知で拒否しなければならない。(SHALL) この拒否は、通常の判定の対象外とした prompt template およびスキル起動にも適用する(拡張コマンドは `input` イベントに届かない)。在職の記録は圧縮の終了イベントおよびエージェント開始のイベントでは下ろしてはならず、gate ハンドラの出口でのみ下ろす。(MUST NOT) 在職中に拒否された入力は、先行して待機している入力のロール・ステップの状態と、その入力の巻き戻しを変えてはならない。(MUST NOT) 圧縮の取り消し(Esc など)は pi の既存の取り消し経路で圧縮を中断させ、システムは取り消された入力について会話リクエストを送らず、状態を復元し、理由に取り消しを名指さなければならない。(SHALL)

#### Scenario: 待ち受け中に届いた入力は送られず理由が返る
- **GIVEN** gate が元の入力のために先行圧縮を待っており、在職が記録されている
- **WHEN** 別の入力が `input` イベントに届く
- **THEN** その入力は送られず、`handled` と 1 件の理由通知が返り、在職中の他の入力の巻き戻しは変わらない

#### Scenario: 在職中のテンプレートとスキル起動も断る
- **GIVEN** gate の先行圧縮の在職中である
- **WHEN** prompt template またはスキル起動のコマンドが `input` イベントに届く
- **THEN** 通常の判定の対象外にかかわらず、送られずに拒否される

#### Scenario: 対話端末で圧縮中にキューされた入力も断られ、本文は追記で戻る
- **GIVEN** 対話端末で gate の先行圧縮が走っており、圧縮中に複数の行がキューされている
- **WHEN** 圧縮の終了処理でキューされた行が順に `input` ハンドラへ届く
- **THEN** それらは送られず、それぞれの本文が入力欄へ追記で戻され、前の行の本文は消えていない

#### Scenario: Esc で先行圧縮を取り消す
- **GIVEN** 対話端末で gate の先行圧縮が走っている
- **WHEN** ユーザーが Esc で取り消す
- **THEN** 圧縮は `/compact` のときと同じく中断し、その入力の会話リクエストは 0 件で、本文は入力欄に戻り、理由は取り消されたことを名指す

### Requirement: 在職中に拒否した入力の戻し方
対話端末では、システムは在職中に拒否した入力について、その本文を入力欄への追記で戻さなければならない。(SHALL) 複数の拒否が順に届いても、前の本文は消えない。RPC では、拒否は `handled` の成功応答と拡張通知として届く。host 自体が圧縮中に到達した prompt に対して返すエラー応答は、この拒否とは別の host の挙動である。

#### Scenario: RPC の拒否は handled 成功応答と拡張通知である
- **GIVEN** RPC セッションで gate の先行圧縮の在職中である
- **WHEN** 別の prompt が届く
- **THEN** 応答は `handled` の成功応答であり、理由の拡張通知が 1 件届き、会話リクエストは発生しない
