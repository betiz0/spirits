# Design

## Context

`docs/spirits-design.md` の層構成（相互に依存しない兄弟層を entry が配線する）が前提。検証ステップは `routing/phase.ts` が `STEP_DEFINITIONS` の starter から追跡しており、`phase.step()` が実行中のステップを返す。ステップ追跡はモデルの選択（`spirits/auto` か物理モデルか）に依存しないが、ルーティング層自体が登録できないランタイムでは `step()` は常に空になる（`index.ts` の `fallbackRoutingPhase`）。

レポートの出力形式と重大度は、既定の検証（`.pi/prompts/opsx-verify.md`、OpenSpec CLI が生成）と深い検証（同梱スキル `sprt-opsx-verify-deep`）の本文が決める。既定の検証のプロンプトは spirits の管理外で、OpenSpec CLI の更新による再生成で書き換わる。

ホスト 1.6.0 の公開型（`packages/spirits/node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/types.d.ts`）で、この変更が使う機構は確認済み:

- `registerTool()` は起動後も呼べて、`defaultActive?: false` で非有効のまま登録できる。`getActiveTools()` / `setActiveTools(names)` は動的登録済みツールにも効く。
- `promptGuidelines` はそのツールが有効なあいだだけ `<rules>` に現れる（docs/extensions.md「Tool Definition」）。
- `on("agent_before_settle")` は `AgentBeforeSettleEvent`（`entries` / `continue` / `context`）を受け取り、`AgentBeforeSettleEventResult`（`BoundaryResult`）を返す最後の作用点。中断された run は `agent_before_settle` を飛ばして `agent_settled` へ行く。

## Goals / Non-Goals

**Goals:**

- レポートの保存先とファイル名を spirits が決め、既存ファイルを上書きしないことを保証する。
- 保存されない検証を「未完了」として利用者に示す。
- OpenSpec が生成するプロンプトの編集に依存しない（再生成されても効く）。
- 検証していないセッションのプロンプトと挙動を変えない。

**Non-Goals:**

- 検証の重大度・判定基準・archive 条件を変えない。
- `sprt-opsx-review-change` の実装前レビューレポートは対象外。
- 既存の変更に入る既存レポート（`d-verify1.md` など）の改名・移行をしない。
- tsrepl のセルから直接ファイルへ書く行為を縛らない（vm はセキュリティ境界ではない、`docs/spirits-design.md`）。
- レポートの中身・言語・形式を変えない。

## Decisions

### Decision 1: 保存は spirits が行い、モデルは本文だけを渡す

**選択肢**: (A) モデルが `write` ツールやリダイレクトで保存する手順をプロンプトに書く。(B) 保存するツールを spirits が持ち、モデルは本文と変更名を渡す。(C) 保存するツールを spirits が持ち、モデルは本文だけ渡す。

(C) を採る。(A) は `.pi/prompts/opsx-verify.md` への追記が必要で、そのファイルは OpenSpec CLI の再生成で消える。さらに「保存し忘れた」を検出できない。保存先・ファイル名・衝突防止という保証したい性質は、すべて spirits 側で決まる値であり、モデルに決めさせる理由がない。(B) を採らなかった理由は Decision 12: 変更名をモデルに申告させると、検証対象と違う変更（たとえばたまたま実在する別変更、複数ストアの同名変更）へ保存できることを仕様上で許してしまう。保存先は検証対象の関数でなければならない。

### Decision 2: 新しい兄弟層 `spirits:verify`

**選択肢**: (A) `commands` 層に足す。(B) `routing` 層に足す。(C) 新しい兄弟層 `spirits:verify` を作り、`spirits:shared` と `spirits:routing` と `host:pi-coding-agent` に依存する。

(C) を採る。(A) は「コマンド表面」ではない処理（ツール登録と run 境界の強制）を `commands` に混ぜ、その層の責務を広げる。(B) はロールの決定と無関係な書き込み処理を `routing` に入れて、層の説明と実態をずらす。(C) は正本の層表と所属表・ARCH-SPIRITS-LAYER の層一覧を同一変更で更新する代价で、新規継ぎ目をレビューに上げ続ける。保存という独立した責務なので代价を払う価値がある。entry 層の許可先に `spirits:verify` を足す。

### Decision 3: 保存先は openspec CLI の解決結果から取る

**選択肢**: (A) `openspec status --change <name> --json` の `changeRoot` を保存先に使う。(B) `openspec/changes/<name>` を nearest root 探索で自前解決する。

(A) を採る。(B) は store 宣言・ストア解決・config ポインタの規則をもう一つ実装することになり、openspec 側の解決規則との重複を作る。検証ステップはすでに openspec CLI を実行するので、新しい外部依存にはならない。実行は `Bun.spawn` にタイムアウトを付け、非ゼロ終了・解析失敗・`changeRoot` 不在は理由付きの失敗として返す。

store の指定（`--store <id>`）も検証を開いたコマンド行から spirits が読み、検証対象の固定と一緒に保持して解決時へ渡す。モデルは store に立ち入れない。store 指定が無いときの解決は openspec の nearest 解決に委ねる。（d-verify1 の W-1 による修正: 初版の実装は store を解決器まで配線したのに検証入力の行から読まなかったため、ストア指定の検証が保存を理由付きで拒否された。入力行から配線するか、本変更の限界として README とここに記録する。）

保持の時刻は**ステップを開いた入力**であり、固定が立った入力ではない。開行が store を含み名前を含まない（聞き返しになる）流れるでは、store は固定より前に預けておかないと失われる。（d-verify2 の C-1 による修正: 初版の配線は store を「pin が立った行」でのみ拾ったため、`/opsx-verify --store s1` → 回答 `alpha` の流れで解決が store なしで走った。`VerifyPin` は固定前の store 保持（例: `rememberStore`）を持ち、固定時は「その行が渡した store → 保持済みの store」の順で採用する。実測ランナーは隔離 HOME で `openspec store setup` を走らせて登録ストアを staging し、store のみ変更の固定と保存、および store に無い変更の拒否を実測している（`evidence/verify-report.json`。）

保持した store は**対象固定と保存の両方**に使う。一覧取得を nearest root で行うと、指定 store だけにある変更は固定されず、ローカルだけにある変更が指定 store の対象として固定される。（d-verify3 の C-1 による修正: `listChangeNames` も store を受け取り、store 指定時は `openspec list --json --store <id>` を使う。固定と保存が異なる root を参照する状態を仕様違反として扱う。）

### Decision 4: ファイル名は種別ごとの連番、種別は実行中のステップから決める

**選択肢**: (A) 実行中のステップから種別を決め、`verify<N>.md` / `d-verify<N>.md` の系列を使う。(B) モデルにファイル名・パスを決めさせる。(C) `verify-<timestamp>.md`。

(A) を採る。prefix は利用者指定で、既定の検証が `verify`、深い検証が `d-verify` である（これまでの archive に既に `d-verify1.md`〜`d-verify5.md` の実例があり、深い検証の歴史名とも揃う）。連番は保存先ディレクトリの同じ系列の**最大値 + 1**（欠番は埋めない。`verify1.md` と `verify3.md` なら次は `verify4.md`）、系列が空なら 1。これまでの archive で `verify1.md`・`deep-verify1.md`・`d-verify1.md` が混在したのは (B) の結果で、系列が人ごとに違うと「何回目の検証か」が読めない。(C) は時系列は保つが連番が読めず、同じ検証の差し替え比較がしにくい。(B) は保存先を決めたい動機そのものに反する。種別と prefix の対応は `src/constants.ts` に置き、モデルの申告では上書きしない。

### Decision 5: 一時ファイル + ハードリンクによる完全な作成と衝突時の再試行

**選択肢**: (A) `flag: "wx"` で最終名へ直接書き、`EEXIST` なら次の連番で再試行する。(B) 存在チェックしてから `w` で書く。(C) 同一ディレクトリの一時ファイル（系列外の名前）へ `wx` で本文を書き切り、最終名へハードリンク（`link`）を張る。`link` が `EEXIST` なら連番を進めて再試行（上限あり）、失敗時は一時ファイルを削除する。

(C) を採る。(B) はチェックと書き込みの間に別の実行が同じ名前を作れる（TOCTOU）。(A) は作成後の書き込み失敗で、途中まで（または空）のファイルが最終名で残る。検証レポートは archive 判断の根拠なので、**最終名に観測されるファイルは完全な本文か不在かのどちらか**でなければならない。(C) は「上書きしない」も満たす: `rename(2)` は既存の最終名を黙って置き換えるため上書き禁止の目的に反し、`link(2)` は既存名に対して `EEXIST` で拒否する。リンクされるのは書き切ったファイルなので、最終名に部分本文が観測される窓もない。途中の一時ファイルは系列外の名前なので採番にも影響しない。（d-verify1 の S-1 による修正: 初版はこの文書に `rename` と書いていたが、rename は目的と矛盾する。実装は当初から `link` を使っており、実装が正しい。）`repl/spill.ts` が `wx` で同じ衝突防止を使っているので、方針は既存と揃う。連番再試行の上限と CLI タイムアウトは別の定数で、根拠を `src/constants.ts` のコメントに書く。

採番と作成の I/O 失敗は、保存要求の失敗理由へ変換する。採番前のディレクトリ消失で `readdir` が例外を投げる状態や、一時ファイル作成後の書き込み失敗で一時ファイルが残る状態は、仕様の「失敗時には理由を返す」「部分内容を残さない」に反する。（d-verify3 の C-2 による修正: 採番を `try` で囲み、今回の処理が作った一時ファイルだけを後始末する。既存ファイルは削除対象にしない。）

### Decision 6: 検証ステップが開いた入力でのみツールを有効にする

**選択肢**: (A) 起動時に `defaultActive: false` で登録し、検証ステップが開いた入力を起点に `setActiveTools()` で追加し、ステップ終了・セッション開始で外す。(B) 常に有効にする。(C) 検証ステップごとに `registerTool()` する。

(A) を採る。(B) は検証しない全セッションのプロンプトにツールと `promptGuidelines` を載せ、誤使用も招く。(C) には登録解除の公開 API がなく、run ごとに登録が増えていく。(A) は `promptGuidelines` が「有効なあいだだけ」現れるというホストの仕様をそのまま使って、検証中だけの指示を注入できる。有効化は `getActiveTools()` を読んでから追加し、外すときも自分が追加した名前だけを除去する（他拡張の選択を上書きしない）。保存成功では外さない: continuing のステップでは保存後に利用者が追加情報を渡して同じ検証を続けることがあり、その時の再保存は新しい連番になる（対象は pin で固定なので別変更には行けない）。有効集合の唯一の解除駆動はステップ終了とセッション開始で、これは検証レポートを保存しなかった run とも無関係に揃う。

有効化は必要条件であって十分条件ではない。`defaultActive: false` でも明示的なツール選択やセッション復帰で有効集合に入り得るため、**ツール実行時にも段確する**: `phase.step()` が検証ステップであり（Decision 12 の）対象が固定済みでなければ、書き込み前に理由付きで拒否する。無効化の駆動はステップ終了（`agent_settled`、中断後も発火）とセッション開始・ツリー移動だけで、保存成功では外さない（前述）。ステップ終了は `agent_settled`（中断後も発火する）で追跡されるので、中断経路もステップ終了側の処理がそのまま覆す。（d-verify1 の S-2 による修正: 初版は「保存成功・ステップ終了・セッション開始で駆動する」と書き、同じ Decision の「保存成功では外さない」と矛盾していた。実装は保存成功で外さない側が正しい。）逆に `opsx-verify` は continuing なので中断後もステップが開いたままで、次の run（保留への回答など）でもツールが見えたままになる。これが Q-2 の引き継ぎに必要な挙動であり、督促フラグとは独立に有効集合を管理する。

入力の扱い順は `routing/register.ts` の後になるよう entry で配線する。ルーティングの `input` ハンドラがステップを起こしたあとに `phase.step()` と `phase.stepStartedByInput()` を読みたい（fit gate が D10 で同じ順序依存を書いているのと同じ型）。

### Decision 7: 督促は `agent_before_settle` で 1 回だけ

**選択肢**: (A) `agent_before_settle` で `custom_message` を 1 回だけ添えて `continue: true`。(B) `turn_end` で毎回要求する。(C) `agent_end` で通知する。

(A) を採る。`turn_end` は 1 つの run 内で応答なしに繰り返せて、条件を誤ると endless loop（host docs の警告）。`agent_end` は最終境界ではなく、リトライやqueued messageの後も続く。`agent_before_settle` は最後の作用点で、中断時は発火しないので「中断時は督促しない」が自然に満たされる。1 回限りのフラグは obligation（ステップを開いた事実）に紐けて持つ。督促の `custom_message` は拡張が書いたメッセージで、スラッシュコマンドもスキル展開も通らない。

保留（検証対象が未固定で、モデルがユーザーに確認を待って終わる run）は督促しない。保留の settle は 1 回限りのフラグを消費せず、保存手段の有効化も維持する（Decision 12）。これで `opsx-verify` の聞き返しフロー（`.pi/prompts/opsx-verify.md` は変更名省略時にユーザーへ尋ねる）が、回答前に督促されることなく続く。


### Decision 8: 督促は保存を強制しつつ捏造も避ける

**選択肢**: (A) 督促メッセージに「検証が未完了なら保存せず、その旨を答えよ」を書く。(B) 無条件に保存を要求する。

(A) を採る。`opsx-verify` は `continuing: true` で、ステップを開いたまま追加情報を待って終わる run があり得る。(B) はそういう run で空レポートか水増しレポートを生む。空・空白のみの本文をツール側で拒否するのと同じ方向の防御で、仕様「保存されるまで検証を完了として扱わない」の意図（検証を実行させ、証拠を残す）と衝突しない。督促を 1 回に絞っているのは、無限ループ回避と捏造圧力の両方のため。

### Decision 9: 保存保証は全モード、追加リクエストは対話モードだけ

**選択肢**: (A) 保存・採番・衝突防止の保証は全モードで効かせ、督促の継続（追加リクエスト）は `ctx.mode` が `tui` / `rpc` のときだけ行い、`json` / `print` は未保存の通知だけする。(B) 全モードで継続する。(C) 保証自体を `tui` / `rpc` のみに限定する。

(A) を採る。保存はツール呼び出しが成否を返すだけで、モードに依存しない。継続だけ切り分ける。(B) はスクリプト実行と CI の非対話実行に誰も応答できない余計なモデルリクエストを足す。fit gate が `tui` / `rpc` を作用域とし、それ以外を fail open にしている（`routing/register.ts` の `gateInScope`）のと同じ切り分けを使う。

通知の経路はモードで実装が違うことを仕様のシナリオに書く: `tui` / `rpc` は `ctx.ui.notify`、`json` / `print` は `process.stderr.write`。後者はホスト 1.6.0 で `ctx.ui.notify` が no-op（`dist/modes/print-mode.js` は `bindExtensions` に ui context を渡さない）であるための代替で、stdout のテキスト出力と JSON イベントストリームの形式は変えない。保存成功そのものはツール結果とモデルの応答（保存先パス）がそのまま出力に乗るので、追加の通知はしない。

### Decision 10: 督促の状態はメモリのみ

**選択肢**: (A) 督促 obligation を extension メモリにだけ持つ（`/reload`・再開・ツリー移動で失う）。(B) `appendEntry` で session に記録し、復帰時に復元する。

(A) を採る。(B) は再開したセッションで、ユーザーが要求していない追加リクエストを走らせる。ステップの追跡自体は session record から復元されるが（`routing/phase.ts` の `followStepRecord`）、obligation は「この run で保存されなかった」という実行時の事実であり、会話の記録ではない。仕様「再読み込みで復帰した検証ステップでは督促しない」と揃う。限界として Open Questions に残す。

### Decision 11: 同梱スキルの本文は条件付きで保存手段へ誘導する

**選択肢**: (A) SKILL.md を「保存手段が有効なら本文を渡す、無ければ従来どおり出力」に更新する。(B) 保存手段を必須とする。

(A) を採る。`sprt-opsx-verify-deep` の frontmatter の `targets` は `spirits, pi.dev, oh-my-pi` で、このスキルは spirits 以外の pi にコピーされても動く。(B) は保存手段が無い環境で検証を成立させない。spirits 内では Decision 6 の有効化が効くので、本文の誘導がなくても督促される。本文を書くのは、保存先パスを報告させる文面をそろえるため。全文のチャット出力は従来どおり維持し（利用者の決定）、保存後もレポート本文を省略しない。

同時に SKILL.md のフェーズ A（未追跡ファイルの内容収集）から、対象変更ディレクトリの検証レポートファイルを除外する。保存が自動化されると `verify1.md` が未追跡ファイルとして生まれ、フェーズ A の読み取り対象に混ざる。レポートは verify 突き合わせ段階でのみ読む証拠であり、差分の証拠として読むのは二重計上と独立性の破壊になる。

### Decision 12: 検証対象は spirits が入力から固定し、モデルの申告では動かない

**選択肢**: (A) ツールが変更名を引き続き受け取り、固定対象と一致しなければ拒否する。(B) 検証ステップを開いた入力と、保留中の後続ユーザー入力から spirits が変更名を抽出し、openspec CLI で一意に解決できるものだけを検証対象として固定する。ツールは本文だけを受け取る。

(B) を採る。(A) はパラメータとして残る以上、モデルが聞き返しで得た名前を正しく再申告する経路に依存し、固定の意味が薄い。(B) では保存先は検証対象の関数になり、検証していない変更への保存は構造的に起こらない。

固定の手順: (1) 検証ステップを開いた入力のテキストからコマンド語以降の第 1 引数を取り、openspec CLI で解決できるなら即固定。(2) 未固定のまま run が終わろうとしたらは督促しない（保留。Decision 7）。(3) 同じセッションの次の `input` イベントでも同じ解決を試み、**ユーザー入力の文字列そのまま**が解決に成功するか、`openspec list --json` の名前の完全一致になる場合だけ固定する。部分一致・曖昧（複数ストアに同名）は固定しない。(4) 未固定のツール呼び出しは書き込まず理由を返す。(5) **一度固定した対象は、ステップ終了・セッション開始・ツリー移動まで動かさない。** 固定後のユーザー入力（`openspec list --json` の別名前の完全一致を含む）では再固定しない。別変更の検証は新しい検証コマンドで開き直す。

（d-verify1 の C-1 による修正: 初版の実装はステップ開信中のすべてのユーザー入力を無条件に `pin.offer()` へ渡し、固定後も別の一覧名で再固定できた。これは Decision 1 が (B) を退けた理由「検証対象と違う変更へ保存できる」をユーザー入力経由で復活させる。`offer` は未固定のときだけ呼ぶ（または `offer` 自身が未固定のときだけ受け付ける）形に直し、固定後の入力で保存先が動かないテストを追加する。）

（d-verify3 の C-1 による修正: 一覧取得の名前解決も保持 store を通す。固定の入力が store を指定している場合、一覧・固定・保存は同じ store の変更集合だけを見る。）

コマンド行の解釈（コマンド語と第 1 引数の切り出し、`/skill:` 接頭辞と空白の定義）は `routing` 側の 1 つの関数（`commandNameFromInput` を「コマンド名 + 第 1 引数」を返す形へ一般化して export したもの）に集約し、`verify` は再実装しない（d-verify1 の W-5。実装が `indexOf(" ")` と `search(/\s/)` に割れているのは 1 箇所に寄せる）。

限度として、ユーザーが自由文（「さっきのヤツ」等）で応答した場合の指示語解決はしない。固定できなければプロンプト側の聞き返しが再度走る設計で、仕様はそれを妨げない。

### Decision 13: 解決処理は関数引数の注入のみで、グローバルな拡張点は作らない

**選択肢**: (A) 製品コードが解決関数を直接呼ぶ。(B) `saveReport(body, resolve)` のように解決処理を関数引数に取り、本番の配線だけが `Bun.spawn` で CLI を呼ぶ薄いラッパーを渡す。(C) セッション単位の DI コンテナを作る。

(B) を採る。連番・排他的作成・link の純ロジックは一時ディレクトリで決定的に試せるが、CLI 解決の失敗系（非ゼロ・解析失敗・`changeRoot` 欠落・タイムアウト）は fake なしには決定的にテストできない。既存コードにもある素朴な関数注入で足りる（例: `routing/register.ts` の `gateInScope` への関数受け渡し）。(C) は新層のためだけの器で過剰。(A) は異常系が実 CLI 依存になり、CI で PATH と cwd に左右される。拡張点はモジュール間のもので留め、公開 API にはしない。

### Decision 14: 聞き返しをまたぐ保証は「ステップが回答の入力まで続く場合」に限定し、未固定で終わった検証は 1 回だけ伝える

**背景（実測）**: 深い検証は `STEP_DEFINITIONS` で `continuing: false`。ルーティングの `agent_settled` ハンドラが自層より先に走るため、対象を変更名として受け取らないまま settle した時点でステップが閉じ、obligation・pin・保存手段の有効化が消える（全セッション共通）。ルーティングが関与しない run（解決されない run）のあとも、次の入力がステップを閉じる。いずれでも保存・督促・通知は無く、回答 run はステップを失ってロックのロールへ戻る（実測: 閉じたあとのロールは `normal`、strong ではない）。両経路とも未保存が無言で終わっていた。

**決定**: (1) 保証範囲 ―― 回答で対象を固定できるのは、ルーティングがステップを維持する場合（spirits/auto の継続する検証ステップ）だけ。深い検証（全セッション）と物理モデルセッションの検証は、検証を開いた行に変更名がある場合にのみ保存と督促を保証する。(2) 未固定のまま窓口が閉じて未保存なら、レポートが保存されていないことと開き直し方（`/opsx-verify <change>`、`/skill:sprt-opsx-verify-deep <change>`）を検証ごとに 1 回だけ伝える（対話は `ctx.ui.notify`、print/json は stderr）。save 拒否理由 `VERIFY_REPORT_UNPINNED_REASON` も、回答で固定できない経路で開き直しを案内する文言に改めた。

**選択肢 3（窓口を開いたまま待つ）を退けた理由**: 深い検証では回答 run が strong ロールで走らないため、窓口を開き続けたまま続けると検証そのものが弱いモデルで走る。開き直しの案内なら強い検証を取り直せる（Decision 7 の督促 1 回規則も薄れない）。**中断時は黙る**（既存の「中断した run では督促しない」と同じ理由: 利用者自身がその run を止めた）。**セッション開始・ツリー移動でも黙る**（Decision 10 と同じ理由で、その run の終わりを見届けた実行ではない）。**別コマンドでワークフローを抜けたときは伝える**（検証がレポート無しで終わった事実は変わらない）。

**obligation の消費は通知の判定より先（d-verify3 C-1）**: 窓口が閉じるときは、通知を行うか否か・対象が固定されていたか否か・中断されたか否かにかかわらず、必ず obligation を消費してから通知可否を判定する。初版は消費より前に早期 return していたため、固定済み（または保存済み）で閉じた検証の obligation が生き残り、直後の無関係な入力が「対象を固定されないまま終わった」通知を誤って出した（pin は clear 済みで、通知文が述べる事実と逆の内容をユーザーへ伝える）。実測: 固定した深い検証を中断 → 後続の入力で通知 1 件、`/opsx-verify alpha` 未保存 → `/opsx-apply` 離脱 → 後続の入力で通知 1 件。変更前のコードは終了時に無条件で obligation を捨てていたので、これは Decision 14 の通知追加で入った回帰である。仕様には要求「対象を固定できないまま終わった検証を伝える」へ消費の SHALL とシナリオ「固定された検証の終了が後日の通知にならない」して書いた。

**検証から検証への切り替え**: 新しい検証を開始する入力は、同じ種類の検証を開き直す場合も旧検証の終了である。新しい pin と obligation を初期化する前に、旧検証の pin と保存状態で終了処理を行う。旧検証が未固定・未保存なら一度だけ通知し、旧検証の通知や督促の状態を新しい検証へ引き継がない。開いたままの検証への通常の回答は切り替えではない。

**開き直しのコマンド語は `STEP_DEFINITIONS` が正**: 「検証を開くコマンドは何か」は `STEP_DEFINITIONS` の starters（`opsx-verify` → `/opsx-verify`、`sprt-opsx-verify-deep` → `/skill:sprt-opsx-verify-deep`）が正で、層の検査もそちらを見る。案内文は可読性のため素の文字列でコマンド語を書くので、starter が改名されたときに文案だけが黙って古くならないよう、`test/constants-verify-report.test.ts` が両 starter 語を `STEP_DEFINITIONS` から引いて案内文定数（`VERIFY_REPORT_NOT_VERIFYING_REASON` / `VERIFY_REPORT_UNPINNED_REASON` / `VERIFY_REPORT_UNPINNED_NOTICE`）に含まれることを検査する（d-verify3 W-3。d-verify4 S-1: 初稿はこの定数を `VERIFY_REPORT_STEP_NOT_OPEN_REASON` と書いていたが、その名前は実在しない。実装と検査が正）。

## 継ぎ目の判断記録（責務と外す条件）

新層 `spirits:verify` とその境界について、F2 の要求する対価の記録。外す条件が書けない継ぎ目は持たせない方針。

| 継ぎ目 | 責務 | なぜこの境界か | 外す条件 |
|---|---|---|---|
| entry → verify（`index.ts` の `optional()`） | 層の配線と劣化時の他層保護 | 兄弟層アーキテクチャの既存パターン | verify が他のどの層にも依存しなくなっても optional() は配線様式として残す |
| verify → routing（`phase.step()` / `stepStartedByInput()` の読み取り） | 検証種別と対象入力の取得 | 種別とステップは routing の専有知識で、モデル選択に依存しない追跡は routing に既にある | routing がステップ読み取りの公開関数（`fallbackRoutingPhase` を含む契約）を失ったら、verify はその時点で層として成立しないので削除し、督促なしの保存ツールへ落とす |
| verify → openspec CLI（`changeRoot` 解決） | 対象変更ディレクトリの解決 | store 宣言・nearest root・config ポインタの規則を再実装しないため | openspec が公開 API で解決結果を出すなら spawn を置換する（規則の再実装だけが増える場合は旧 rule として残さない） |
| `spirits_verify_report_save` ツール | 本文を受け取る唯一の書き込み経路 | 保存し忘れの検出と衝突防止の作用点 | 保存が検証プロンプト側で保証される仕組みが OpenSpec 側に入ったらツールと督促を同時に削除する |
| `agent_before_settle` 督促 | 未保存の run を 1 回だけ戻す | 最後の作用点で、中断時に発火しない仕様が「中断時は督促しない」に一致 | 督促が空・水増しレポートを量産すると実測で分かれば督促だけ外し（保存成功通知と stderr 通知は残す） |
| obligation / pin のメモリ状態 | 督促 1 回と対象固定の保持。窓口の終了では通知の可否とかかわらず obligation を必ず消費する（d-verify3 C-1） | 実行時の事実であり会話の記録ではない（Decision 10） | セッション永続化が必要になる運用実測があるまでメモリのみ |

## Risks / Trade-offs

- [Risk] 督促が空レポート・水増しレポートを誘う → Mitigation: Decision 8 の文言、空・空白のみ本文の拒否、督促を 1 回に限定、中断時は督促しない、対象未固定（保留）は督促しない。
- [Risk] `openspec` CLI が PATH に無い、遅い、`changeRoot` を返さない → Mitigation: タイムアウト付き実行と理由付き失敗。失敗時は書き込まず、obligation は残るので通知までに至る。
- [Risk] `setActiveTools()` が他拡張の有効ツール選択を壊す → Mitigation: `getActiveTools()` を読んで和集合で追加し、自分が追加していない名前は除去しない。テストで他ツール名を混ぜて確認する。
- [Risk] `opsx-verify` は continuing なので、ステップが開いたまま同じ検証を複数回保存しうる → Mitigation: 保存ごとに新しい連番になり、対象は pin で決まるので既存の上書きも別変更への保存も起きない。ツールはステップ開いている間だけ有効で、終了時に必ず外れる。
- [Risk] pin 解決がユーザー入力の完全一致だけなので、自由文の応答だといつまでも未固定で督促が保留される → Mitigation: 未固定は督促しない設計なので誤督促は起きない。聞き返しはプロンプト側が再度走らせる。固定されないまま保存されたレポートは仕様上存在しない（ツールが未固定を拒否する）。
- [Risk] ルーティング層が登録できないランタイムでは `step()` が空で、有効化も督促も効かない → Mitigation: 既存の劣化層の通知（`index.ts` の `DEGRADED_NOTICE`）に新層を載せて、そのランタイムでは保証しないことを明示する（保存手段は非有効のままなので、動作は現状の「チャットに出力するだけ」に戻る）。
- [Trade-off] `promptGuidelines` による注入は、有効化のたびに system prompt の差分を 1 回発生させる（host docs の cache 記述）。検証中のみで、run 回数のオーダーに収まる。
- [Trade-off] `verify` と `d-verify` を別系列にすると、同じ回数だけ走っているとは限らない。deep verify は verify の後段なので、系列を分けないと「深い検証の 2 回目」が `verify3.md` になるほうが誤読される。
- [限界（実測）] 物理モデルセッション（`spirits/auto` にしない運用）では、routing の「リクエストを解決しなかったステップは次の idle input で終わる」規則が毎回発火し、`requestResolved` が永遠に走らないため、検証ステップは初回 run の直後の入力で閉じる。初回 run の settle での保存と督促は効くが、聞き返しをまたぐ保存窓口と回答後の督促は効かない。Mitigation: 実測は運用の標準である `spirits/auto` で行い（`evidence/verify-report.json`）、物理モデル側の挙動は routing の既存セマンティクスの範囲なので本変更では変えない（変更するなら dual-model-routing 側の話）。Decision 14 がこの範囲を仕様に書き、閉じたときは開き直しを 1 回伝える。
- [限界（実測、Decision 14）] 深い検証は `continuing: false`（全セッション）なので、聞き返しをまたぐ保証は適用されない。解決されない run のあとの回答 run はステップを失い、ロックのロール（strong ではない）で走る。Mitigation: 未固定で閉じた検証は 1 回だけ通知し、変更名付きで開き直して強いロールで走り直してもらう。

## Migration Plan

既存の変更ディレクトリのレポートファイルは改名・移動しない。この変更の後は新規保存が spirits 側で決める連番になり、古い名前はそのまま読める。ロールバックは層の登録を外すだけで、保存済みのファイルはただの markdown なので影響しない。

## Open Questions

- 督促 obligation と pin を `/reload` 後も復元するか（Decision 10 で復元しないと決めた限界）。復元する場合は、再開時に督促してよいかの条件を先に決める必要がある。
- 自由文での検証対象応答（「さっきの」等）のピン留めはしない（Decision 12 の限度）。実運用で聞き返しが往復しすぎるなら、`openspec list --json` の名前による入力内の部分候補提示をプロンプト側の責務として検討する（spirits 側は変更しない）。
