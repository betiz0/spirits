### Requirement: 公式型による型検査
システムは、`packages/spirits` の固定した公式パッケージ (`@earendil-works/pi-coding-agent` / `@earendil-works/pi-tui`) を devDependency として完全一致で保持し、ホストの型を実型として `tsc --noEmit` で検査しなければならない。(SHALL) `packages/spirits/src/types/` にホスト型の再宣言 (型ミラー) を置いてはならない。(MUST) ホストへ渡してホストが所有する値を返す契約 (描画 component など) を `packages/spirits/src` の他の場所の手書き interface で再宣言してはならない。(MUST) この境界の規約は `docs/architecture/convention-registry.md` の `ARCH-PI-BOUNDARY` を正とする。(SHALL) `packages/spirits` の解決が root の workspace 経由で fork のソースへ向いてはならない。(MUST) `scripts/check-pi-type-mirror.ts` を置いてはならない。(MUST)

#### Scenario: 実型で検査する
- **WHEN** `packages/spirits` で `bun run check` を実行する
- **THEN** ホストの公開型を固定 devDependency の実体から解決し、型エラーが 0 件である

#### Scenario: 型ミラーを置かない
- **WHEN** `packages/spirits/src/types/` を調べる
- **THEN** ホスト API の再宣言 (型ミラー) が無い

#### Scenario: 公開面の外は失敗する
- **WHEN** `@earendil-works/pi-coding-agent/core/session` のように `exports` に無い subpath を import する
- **THEN** `tsc` はその specifier を解決できず失敗する

#### Scenario: component 契約を handwritten にしない
- **WHEN** 起動ヘッダ、TODO パネル、`/spirits-role` の一覧が実装する描画 component の契約を調べる
- **THEN** いずれもホストの公開 export から導いた component 型に代入可能であり、手書きの component interface は `packages/spirits/src` に存在しない
- **AND** ホストが所有する返り値の配列を in-place で変更するコードを `tsc --noEmit` が失敗させることを、一時の編集ではなく test に残した用例で継続的に検証している
- **AND** 代入可能性の用例は、実装から受け取った component を cast せずにホスト由来の型で受け、未捕捉を失敗として扱う (cast は代入可能性を証明しない)

システムは、ホストの版を更新したとき、固定した公式 artifact と対象 commit の拡張 bundle で互換性ランナーの公式モードを実行し、必須観測が `confirmed` であり、失敗が 0 件であることを確認しなければならない。(SHALL) 必須観測の `limited` / `unavailable` / `not-run` を成功として扱ってはならない。(MUST NOT) 判定はランナーの `Compatibility met` を正とし、`managed-pi-compatibility` の「必須観測の `limited` を成功に数えない」と食い違わない形にしなければならない。(SHALL)

#### Scenario: 公式モードの成功
- **WHEN** 公式 artifact で互換性ランナーを実行する
- **THEN** 必須観測がすべて `confirmed` で `failed` が無く、結果に公式モードの識別情報が記録される

### Requirement: tmux 検証
システムは、ホストの版を更新したとき、ビルドした起動役と対象版の managed 一式を tmux 検証ランナーで起動し、起動ヘッダ、`/spirits-clear` による会話境界、`tsrepl` のセル実行、`/spirits-role` の一覧と role lock の status 行への追従、および TODO パネルの表示と折りたたみキーを確認しなければならない。(SHALL) 検証は、据え置いた対象版の一式が実際に使われている環境で行い、各観測を同一の pane で終えた後にその pane を終了して、検証ランナーの回収を確認しなければならない。(MUST) pane を終わらせるコマンドは新版 host の終了コマンド (`/quit`) とし、効かない場合の代替 (`C-d`) を併記しなければならない。(MUST NOT) 起動引数を変える観測 (モデル選択の正常 / 無一致など) は別の run として起動し、それぞれの run を同じ手順で回収しなければならない。(MUST) 検証は、検証ランナーの状態置き場を隔離先に固定し、検証が使うポートを予約して `run` と `check` の両方に渡さなければならない。(MUST) 検証ランナーは検証後にプロセスと一時リソースを回収しなければならない。(MUST)

#### Scenario: 対話起動の確認

- **THEN** ペインのプロセス、セッション、確保した一時リソースやポートが残っていない
- **AND** 回収確認は、検証が予約したポートを明示的に検査した結果であり、ポートを渡していない `check` の `clean` を回収の証拠として扱っていない

#### Scenario: 終了コマンド

- **THEN** 新版 host の終了コマンドが書かれており、終了が効かない場合の代替が書かれている
- **AND** 起動引数を変える観測を別の run として起動し、その run も回収することが同じ節に書かれている

- **THEN** 会話境界が切れたこと、一覧の各行、status 行の badge の追従、TODO パネルの項目と折りたたまれた表示が画面に現れる

### Requirement: 旧版への戻し方
リポジトリは、新しい起動役が動かないときの戻し方を文書に保持しなければならない。(SHALL) 文書は、`~/.spirits/bin` の退避、直前の spirits リリースの実行ファイルと managed 一式の双方を同じリリースから、SHA256 を検証して戻す手順、戻した後に起動役と導入済みの一式の版がどちらも期待どおりであるのを確認する手順、および `~/.spirits/agent` のデータが消えないことを含まなければならない。(MUST) 導入済みの set を作り直すコマンドが現在の set を基準にすること、および agent dir のデータが消えないことと旧版がそのデータを読めることが別の事実であることを文書は明示しなければならない。(MUST) 文書は、廃止した fork 経路 (`SPIRITS_ROUTE`) を戻し方として案内してはならない。(MUST NOT)

戻し方は、検証が通るまで既存のファイルを差し替えてはならない。(MUST NOT) SHA256 の検証が失敗したときに、配置や削除の命令へ進まないことを、検証の終了コードで示さなければならない。(MUST) 戻し方は、検証した配布物と同じ組を導入することを以て成立とし、導入コマンドが別の配信元や現在の set を基準に再取得する経路に乗らないことを示さなければならない。(MUST) 戻し方は、managed agent root 配下の agent dir (`~/.spirits/managed-pi/agent`) に置かれた設定とセッションを削除してはならない。(MUST NOT) 戻し方の正本が 1 つであり、他の文書は同じ検証・同じ差し替え順序と食い違わない案内にとどめなければならない。(MUST)

#### Scenario: 検証が失敗したら配置しない
- **WHEN** 戻し方のコマンドで SHA256 の検証が失敗する
- **THEN** 実行ファイルも一式も配置されておらず、既存の起動役と導入済みの一式がそのまま残っている
- **AND** 検証のコマンドと配置のコマンドが同じ論理的な块になっており、検証の失敗が配置へ流れないことがコマンドの形で読み取れる

#### Scenario: 検証した組を導入する
- **WHEN** 戻し方で managed 一式を導入する手順を読む
- **THEN** 検証済みの manifest と bundle を明示した導入であり、既定の配信元解決や `SPIRITS_MANAGED_PI_MANIFEST_URL` の値に左右される案内になっていない

#### Scenario: 一式の削除で隔離データが消えない
- **WHEN** 戻し方の削除・置換の対象を読む
- **THEN** `~/.spirits/managed-pi/agent` 配下の設定とセッションを対象に含めないことが書かれており、導入済み一式の差し替えが隔離した agent dir を消さないことが確認できる

#### Scenario: 戻し方の確認
- **WHEN** リリース後の手順書を確認する
- **THEN** `~/.spirits/bin` の退避先、直前のリリースの実行ファイルと managed 一式の取得元と SHA256 検証、一式を作り直すコマンド、`~/.spirits/agent` を消さない旨が記載されている
- **AND** 戻した後の起動役の版と導入済みの一式が指すホスト版の両方を確認する手順が記載されている

#### Scenario: 一式の作り直しでは戻らない
- **WHEN** 手順書の managed 一式の作り直しの扱いを読む
- **THEN** そのコマンドが導入済みの set を基準にするため、実行ファイルだけを戻した場合にそれを走らせると新しい版の一式が再導入され得る旨と、同じリリースの一式を明示して戻す方法が記載されている

#### Scenario: fork 経路を案内しない
- **WHEN** 手順書の戻し方を読む
- **THEN** `SPIRITS_ROUTE` を戻し方として指定する案内が無く、フォーク Era の実行ファイルの再ビルドは managed 経路の戻し方の後続に歴史的な手段として置かれている

## ADDED Requirements

### Requirement: ホスト版の候補選定
システムは、ホストの更新対象の版を、公式リリースとして公開済みで、対象 platform の配布物とその SHA256 がリリースの検証ファイルに並び、対応する公式型パッケージが両方公開済みで、`bunfig.toml` の公開後経過時間の門を過ぎている版から選ばなければならない。(SHALL) 選定した版は 1 つの変更の中で固定し、手順書は、選定した版、その公開日時、配布物の SHA256、門を過ぎていることの判定を記録しなければならない。(MUST) 手順書は、門の条件を実行コマンドと照合する値の並びとして書き、候補を棄却した場合は棄却した版、満たさなかった条件、欠けていた配布物または型パッケージの名前を記録して固定値を変更しない手順を記載しなければならない。(MUST)

#### Scenario: 門を過ぎていない候補
- **WHEN** `bunfig.toml` の `[install] minimumReleaseAge` が要求する経過時間を過ぎていない版を更新対象にしようとする
- **THEN** その版は選定せず、理由を記録して固定値を変更しない

#### Scenario: 検証ファイルに無い配布物
- **WHEN** 対象 platform の配布物の SHA256 がリリースの検証ファイルから見つからない
- **THEN** その版は選定せず、理由を記録して固定値を変更しない

#### Scenario: 型パッケージが揃わない候補
- **WHEN** 対象版の公式型パッケージの一方が未公開または経過時間の門を過ぎていない
- **THEN** その版は選定せず、どちらが欠けているかを記録して固定値を変更しない

#### Scenario: 棄却の記録
- **WHEN** 手順書の候補選定を読む
- **THEN** 経過時間の不足、検証ファイルに無い配布物、型パッケージの欠落を個別に判定し、棄却した版と理由と欠けたパッケージ名を記録して固定値を変えずに停止することが、採用の記録と同じ書式で記載されている

#### Scenario: 選定後の新しい stable
- **WHEN** 選定を記録した後、進行中の変更の対象版より新しい適格な stable が現れる
- **THEN** 進行中の変更の対象版は動かない
- **AND** 新しい版は別の変更として選定し直し、その変更で型の検査と配布物の検証をやり直す

#### Scenario: 選定根拠の記録
- **WHEN** 更新対象の版を決めた手順書の節を読む
- **THEN** 版、公開日時、対象 platform の配布物名と SHA256、経過時間の門の判定、およびその版を本変更で固定することが記録されている

### Requirement: ホストの推移依存の採用
システムは、ホストの版が連れてくる実行時依存を、対象版の公式配布物と公式型パッケージが宣言する集合としてそのまま採用し、spirits 側に依存ごとのラッパーまたは互換層を追加してはならない。(MUST) 変更は、前の版との差分として増減した推移依存、およびその版で利用者に見える形で挙動を変える上流の変更を記録し、採用を取り消す条件を記録しなければならない。(MUST)

#### Scenario: 差分の記録
- **WHEN** 更新の変更の記録を読む
- **THEN** 前の版と対象版で増減した推移依存の Package 名と版、`bun.lock` の移動として現れる範囲、および上流の挙動変更のうち利用者に影響するものが記載されている

#### Scenario: ラッパーを増やさない
- **WHEN** 対象版の推移依存を受けるための新しい層または interface を変更内の計画で調べる
- **THEN** 依存ごとのラッパーまたは互換層は追加されていない

#### Scenario: 取り消す条件
- **WHEN** 採用の記録を読む
- **THEN** どのような実測結果が出たら対象版の採用を取り消して前の pin に戻すかが記載されている
