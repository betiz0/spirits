# spirits M5 設計書: Phase 2 群(判断ゲートつき)

- フェーズ: M5 / 版 v1.0 / 2026-10-07
- 前提文書: spirits 設計書 v0.4(§4.2, §4.3)、M1–M4 設計書

## 1. 目的と位置づけ

M5 は「実装フェーズ」である前に **採否判断フェーズ**である。M1–M4 を実運用した計測・実感を根拠に、以下の 2 件を個別に Go / No-Go 判断し、Go のものだけ実装する。

1. セル評価 Phase 2(パーサによる最終式自動返却 + import 宣言の `use()` 変換)
2. rlm 非同期 fan-out(ハンドル即時返却 + 後回収)

両方 No-Go でも M5 は「判断を記録して完了」でありうる。

## 2. 依存関係ルール

**許可:** M1–M4 全成果物と、その運用で得た計測データ

**禁止:** なし(本フェーズが最終段のため)。ただし M1–M4 の公開 API を破壊する変更は別途設計書改訂を必須とする

## 3. 判断ゲート 1: セル評価 Phase 2

### 判断材料(M1–M4 運用で収集する指標)

| 指標 | 収集方法 |
|---|---|
| セルのトランスパイル/実行エラー率 | tsrepl 実行ログ(error 有無) |
| 「最終式を書いたのに値が返らない」系の失敗頻度 | エラーログ + セッションの手観察 |
| `use()` 呼び出し回数と import 宣言混入率 | use のログ |

### Go 基準(いずれか充足で Go 検討)

- 最終式未捕捉に起因するやり直しがセッション平均 1 回以上見られる
- import 宣言を書いてエラーになるパターンが頻出している

### Go の場合の実装方針

- 軽量パーサを依存追加(acorn 系を候補。Bun 標準に AST API は無いため外部依存は不可避。追加時は設計書 §5-7 のピン留め規律に従う)
- 末尾式文の検出→ `return (...)` 書き換え、先頭 import 宣言の検出→ `await use()` 書き換え
- M1 スパイク結果(`vm.SourceTextModule` の可否)を参照し、真の ESM セル実行とパーサ方式のどちらを採るかもここで再評価
- Phase 1 方式(明示 return/out)は後方互換で残す

## 4. 判断ゲート 2: rlm 非同期 fan-out

### 判断材料

| 指標 | 収集方法 |
|---|---|
| 1 セッションあたりの rlm 呼び出し回数・総待ち時間 | `rlm_usage` エントリ集計 |
| 「同じ rlm を並列で回したかった」場面の有無 | 実運用メモ |

### Go 基準

- 同期的直列呼び出しの待ち時間が実害(セッション体感を損なう)レベル、かつ並列化で構造的に短縮できる場面が確認できる

### Go の場合の実装方針

- `rlm.spawn(prompt)` → 即時ハンドル、`rlm.collect(handle)` → 結果回収、の 2 関数を Registry に追加(既存の同期 `rlm()` は維持)
- 上限並列数(既定 4)と深度制限の併用
- 参考実装: Prime Agent の agent_message 回収モデル。ただしホスト側メッセージング機構は薄く保ち、ハンドルの Promise を Map で管理する程度から始める

## 5. 判断手順

1. M1–M4 リリース後、2 週間のドッグフーディング期間を設ける
2. §3/§4 の指標を集計し、`docs/decisions/m5-gate.md` に Go/No-Go と根拠を記録(ADR 形式)
3. Go の項目のみ本設計書に実装詳細を追記(v1.1)して着手

## 6. 完了条件

- ADR が記録され、Go 項目があれば実装・テスト完了、No-Go 項目は却下理由が明文化されている

## 7. リスク

- **判断材料不足で感覚的 Go になる**: 指標ログの収集を M1/M3 段階から埋め込んでおくことで防止(要求は M1: tsrepl ログ、M3: rlm_usage)
